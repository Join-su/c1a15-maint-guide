# 평가 카드 30건 작성 지시

당신은 정비 Agent를 평가할 **시험지(평가 카드)** 작성자다. 실제 공장의 숙련 정비자라고 생각하고, 아래 입력만 보고 알람 30건 각각의 "숨은 정답 원인"과 "정비자가 각 점검에서 보게 될 결과·메모"를 쓴다.

## 읽을 수 있는 파일 (이 폴더 안의 세 개뿐)

- `alarms.json` — 알람 30건(카드 ID, 설비, 시각, 증상군, 알람 값·경계, 센서 값, 같은 설비의 직전 측정 최대 12회)
- `MG-MM.md` — 가상 정비 매뉴얼(증상군별 원인 후보, 점검 절차, 판정 기준, 등급)
- `manual_sections.json` — 같은 매뉴얼의 절 목록(절 ID, 점검이 연결된 원인, 확정형/선별형)

**이 폴더 밖의 파일·폴더는 어떤 것도 읽거나 검색하지 않는다.** 다른 저장소, 정비 이력, 데이터 생성 코드, 원본 CSV를 찾아보지 않는다. 최종 보고에 실제로 읽은 파일 경로를 모두 적는다.

## 만들 파일

이 폴더에 `cards.jsonl`(한 줄에 카드 하나, 30줄, `alarms.json`의 카드 순서)을 만든다. 형식:

```json
{
  "card_id": "EC-01",
  "hidden_cause": {"type": "manual_cause", "code": "CL-1", "description": "흡기 필터에 기름때가 쌓여 냉각 공기 부족"},
  "precheck_memo": "하우징 표면 54 °C, 공기·공정 온도 기록",
  "check_results": {
    "4.3": {"result": "이상", "memo": "필터 표면 대부분 기름때로 덮임"},
    "4.4": {"result": "정상", "memo": "축 유격 없음, 날개 손상 없음"},
    "4.5": {"result": "정상", "memo": "수위 MIN–MAX 중간"},
    "4.6": {"result": "정상", "memo": "팬 속도·펌프 설정 표준값과 같음"}
  },
  "restart": {"after_fix": "경계 이내", "without_fix": "여전히 밖"},
  "memo_style": "clear",
  "expected_outcome": "원인 확정",
  "author_rationale": "온도 차가 경계 아래이고 회전수·토크는 평소 범위라 냉각 계통 중 가장 흔한 필터 막힘으로 정함"
}
```

필드 규칙

- `hidden_cause.type`: `manual_cause`(매뉴얼 원인) / `none`(이상 없음 — 일시적 이탈) / `out_of_graph`(매뉴얼 원인 목록에 없는 원인). `code`는 `manual_cause`일 때만, 그 카드 증상군의 원인 코드 중 하나.
- `check_results`: 그 카드 **증상군의 점검 절 전부**(`manual_sections.json`에서 그 증상군의 `kind: check` 전부, C·D등급 포함)를 키로 둔다. `result`는 `정상` / `이상` / `확인 불가`.
- `restart.after_fix`: 원인 조치를 마친 뒤 재가동하면 값이 어떻게 되는가. `restart.without_fix`: 조치 없이 재가동하면 어떻게 되는가.
- `memo_style`: `clear` 또는 `ambiguous`(결과가 메모만으로 분명하지 않은 표현. 예: "좀 지저분한 편", "소리가 약간 다른 것 같음").
- `expected_outcome`: `원인 확정` / `이상 없음·감시` / `숙련자 인계`.
- `author_rationale`: 센서 값과 매뉴얼 근거로 왜 그 정답을 골랐는지 1~3문장.

## 작성 규칙

1. **정답 수:** `out_of_graph` 정확히 3건, `none` 정확히 5건, `manual_cause` 22건.
2. **정답은 센서 값과 매뉴얼로 추론한다.** 예: 매뉴얼 개요가 "주로 출력 과다"·"주로 출력 부족"으로 설명하는 원인은 알람 방향과 맞춘다. 같은 증상군 안에서도 원인을 고루 쓰고(가능하면 증상군의 원인을 한 번 이상), 한 원인에 몰지 않는다.
3. **결과의 일관성:**
   - `manual_cause`: 그 원인의 확정형 점검은 `이상`. 그 원인에 선별형 점검(3.5, 5.5)이 있으면 그것도 `이상`. 나머지 점검은 `정상`. `restart.after_fix`는 `경계 이내`, `without_fix`는 `여전히 밖`. `expected_outcome`은 `원인 확정`.
   - `none`: 모든 점검 `정상`. `restart.without_fix`는 `경계 이내`. `expected_outcome`은 `이상 없음·감시`.
   - `out_of_graph`: 매뉴얼 점검은 모두 `정상`. 그중 한두 점검 메모에 매뉴얼 원인과 맞지 않는 이상 징후(예: 배관에서 물이 샘, 소재 표면 균열, 바닥 진동이 이웃 설비에서 전달됨)를 적는다. `restart.without_fix`는 `여전히 밖`. `expected_outcome`은 `숙련자 인계`.
   - `확인 불가`는 카드당 최대 1개, 정답을 가르는 점검(정답 원인의 확정형·선별형 점검)에는 쓰지 않는다.
4. **메모는 현장 정비자의 말투**로, 본 것·들은 것·수치를 적는다. 원인 이름을 메모에 직접 쓰지 않는다(예: "필터 막힘"이 아니라 "필터 표면 대부분이 기름때로 덮임"). 판정 기준의 수치(절반 이상, MIN 선, 2.8 mm/s 등)를 자연스럽게 쓴다.
5. `memo_style: ambiguous`는 4~6건. 단, ambiguous라도 `result` 값은 정답과 맞게 둔다.
6. 카드끼리 메모 문장을 복사해 쓰지 않는다.

## 끝나면 보고할 것

- `cards.jsonl` 경로와 줄 수
- 정답 유형별 건수, 원인 코드별 건수, `memo_style` 건수
- 실제로 읽은 파일 경로 전부
- 정하기 애매했던 카드와 그 이유
