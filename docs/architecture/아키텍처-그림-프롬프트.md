## Agent 지시

당신은 위 프로젝트의 **시스템 아키텍처 그림**을 만든다. 관련자에게 보여 줄 자료다. 아래 0~8장을 순서대로 지킨다. 이 문서의 규칙과 예시(부록 A·B)가 다른 디자인 습관보다 우선한다. 규칙으로 정할 수 없는 상황이면 임의로 정하지 말고 사용자에게 묻는다.

### 0. 재현 기준

| 항상 같아야 하는 것 (변경 금지) | 시스템마다 달라지는 것 |
|---|---|
| 그림 범위(1장), 절차(2장), 레인 x 범위와 배치 규칙(3장), 연결 표기(4장), 색·글자·선(5장), HTML 조각의 class·스타일(6장), 파일 이름·렌더·검증(7장), 보고 형식(8장) | 레인마다 상자 개수·내용·세로 위치·높이, 실행 경계의 종류와 수, 연결선의 경로와 라벨 위치 |

부록 A·B와 나란히 놓았을 때 **같은 사람이 같은 규칙으로 만든 그림**으로 보여야 한다. 예시의 상자 구성을 흉내 내지 말고, 대상 시스템의 실제 구성 요소만 그린다.

### 1. 그림의 범위

- 그리는 것: **구성 요소와 그 사이의 연결 관계**. 누가 누구를 무엇으로 부르는지(HTTP, gRPC, 함수 호출, SQL, 메시지 발행·구독, 파일 쓰기 등).
- 그리지 않는 것: 구성 요소 내부 처리 흐름(단계, 상태, 분기, 알고리즘), 함수·클래스 목록, 화면 세부, 일정, 담당자.
- 실행 단위 안의 구조는 "어떤 계층·모듈·패키지가 있는지"까지만 보인다. 항목은 칩(`.mod`) 2~5개로 요약한다.
- 구성 요소 = 실행되는 단위(프로세스·컨테이너·함수·앱), 데이터를 담는 곳, 바깥 시스템. 라이브러리 하나하나, 운영체제 기본 기능(파일 선택 창, 시스템 알림 등), 사람이 손으로 하는 관리 작업은 구성 요소가 아니다(필요하면 칩이나 설명으로).

### 2. 그리기 전 절차 (생략 금지)

1. 기준 문서·코드를 읽고 구성 요소 후보와 연결 후보를 뽑는다. **문서·코드로 확인되는 사실은 묻지 않는다.**
2. 사실로 정해지지 않는 갈림길만 **한 번에 한 질문씩** 묻는다. 질문 도구가 있으면 쓰고, 선택지는 2~3개, 첫 선택지에 `(권장)`을 붙이고, 선택지마다 차이를 개발 경험이 적은 사람도 이해할 쉬운 말로 설명한다. 갈림길 목록(해당하는 것만):

| # | 갈림길 | 언제 묻나 | 권장안 기준 |
|---|---|---|---|
| G1 | 사용자·클라이언트: 누가·무엇이 시스템을 쓰나(사람+기기, 장비, 다른 시스템), 앱이 어디서 실행되나(브라우저, 모바일, 데스크톱, 서버에서 그리는 화면) | 항상(문서로 정해지지 않으면) | 문서에 나오는 역할·기기 |
| G2 | 화면 기술: 서버에서 그리는 화면(Streamlit·템플릿 등) / 기기에서 실행되는 앱(웹 프론트엔드·모바일 앱) | 화면이 있고 기술이 정해지지 않았을 때 | 정해진 화면 디자인을 그대로 만들어야 하면 기기에서 실행되는 앱 |
| G3 | 진입점: 웹 서버·API 게이트웨이·로드밸런서·메시지 브로커 수신부를 둘지, 앱 파일 제공과 API 중계를 한곳에서 할지 | 바깥에서 들어오는 연결이 있을 때 | 진입점 하나가 앱 파일 제공 + API 중계 |
| G4 | 실행 단위 나누기: 하나 / 여러 개(서비스·워커·함수·배치 작업) | 업무가 여러 갈래일 때 | 근거가 없으면 하나 |
| G5 | 실행 단위 안 구조: 계층·패키지와 그 관계(같은 프로세스에서 import / 별도 프로세스·원격 호출) | 핵심 로직이 별도 패키지·모듈로 있을 때 | 같은 프로세스에서 import |
| G6 | 실행 단위 사이 통신: 동기(HTTP·gRPC) / 비동기(큐·이벤트) | 실행 단위가 둘 이상일 때 | 응답을 기다려야 하면 동기, 아니면 비동기 |
| G7 | 데이터·상태: 저장소 종류(DB·캐시·큐·파일 저장소)와 하나로 둘지 용도별로 나눌지 | 저장소가 있을 때 | 근거가 없으면 종류별 하나 |
| G8 | 실행 경계: 단일 호스트(Docker Compose 등) / 클러스터(Kubernetes 등) / 클라우드 관리형·서버리스 / 사용자 PC 로컬 / 경계 여러 개 | 배포 방식이 문서로 정해지지 않았을 때 | 문서·코드의 실행 방법 |
| G9 | 외부 의존: 외부 API·SaaS·인증 서비스, 조건부로만 쓰는지 | 외부 호출이 있을 때 | 운영 중 호출되는 것만 |
| G10 | 운영 외 작업: 빌드·CI, 한 번 실행(초기 적재·마이그레이션), 분리 실행(평가·부하 테스트) | 해당 작업이 있을 때 | **운영 중 연결 또는 실행 경로가 확인되는 것만** 넣음. 학습용 Notebook, 단위 테스트, 개발자 개인 실행 방식은 넣지 않음 |
| G11 | 위치가 애매한 기능(검색 색인, 캐시, 인증 등)을 어느 구성 요소에 둘지 | 문서가 위치를 정하지 않았을 때 | 그 기능을 쓰는 실행 단위 안 |

3. 답을 모아 아래 두 표로 보여 주고 "이대로 진행 / 고칠 부분 있음 / 지금은 하지 않음"으로 확인받는다. 확신이 95% 이상일 때만 그린다.
   - 구성 요소 표: `| 레인 | 구성 요소 | 내용 |` (실행 경계 안 / 밖 표시)
   - 연결 목록: `1. A → B: 프로토콜. 무엇을 주고받는지` 형식, 번호 붙임
4. 구성 요소가 많아 3장의 용량을 넘으면, 그리기 전에 "전체 개요 1장 + 영역별 상세"로 나눌지 사용자에게 묻는다(3장 크기 규칙).
5. 질문 없이 정한 작은 결정은 8장 보고의 "질문 없이 정한 점"에 적는다.
6. 기준 문서에 "미정"이지만 현재안이 적혀 있으면 현재안대로 그리고 "확인이 필요한 점"에 적는다. 프로토콜·기술이 문서에 없으면 지어내지 말고 용도만 라벨에 적은 뒤(예: `API 호출 · 문자 발송`) "확인이 필요한 점"에 적는다. 기술에서 바로 정해지는 프로토콜(PostgreSQL → `SQL`, 브라우저 → `HTTP`)은 적어도 되지만, 암호화 여부(HTTPS·TLS)처럼 문서에 없는 세부는 붙이지 않는다.

### 3. 역할 레인과 배치

캔버스 1600×900, 흰 바탕. 요청이 왼쪽에서 오른쪽으로 흐른다. 구성 요소마다 아래 레인 중 하나에 넣는다. **레인 x 범위는 고정**이다. 비어 있는 레인은 비워 둔다.

| 레인 | x 범위 | 넣는 것 | 판단 기준 |
|---|---|---|---|
| L1 사용자·클라이언트 (경계 밖) | 40–222 (w 182) | 사람+기기, 장비·센서, 우리 시스템을 부르는 다른 시스템 | 연결을 **시작하는** 바깥 쪽 |
| L2 진입·트리거 (경계 안) | 266–476 (w 210) | 웹 서버, API 게이트웨이, 로드밸런서, 바깥 연결을 받는 메시지 브로커, 서버에서 그리는 화면 서버, 스케줄러·이벤트 발생기 | 바깥 연결을 처음 받거나, 실행 단위를 깨우는 것 |
| L3 실행 단위 (경계 안) | 540–902 (w 362) | API 서버, 서비스, 워커, 함수, 배치 작업, 로컬 프로세스 | 업무 로직이 도는 곳 |
| L4 데이터·상태 (경계 안) | 980–1250 (w 270) | DB, 캐시, 내부 큐·이벤트 버스, 파일·객체 저장소, 색인 | 데이터를 담거나 실행 단위 사이를 잇는 저장·전달 장치 |
| L5 외부 서비스 (경계 밖) | 1320–1556 (w 236) | 외부 API, SaaS, 외부 인증, 알림 서비스 | 우리가 부르는 바깥 시스템 |
| 아래 줄 (경계 밖) | 칸1 40–510, 칸2 560–882, 칸3 980–1250, 칸4 1300–1556 | 운영 외 작업: 칸1 빌드·CI·프론트엔드 코드, 칸2 분리 실행(평가·부하 테스트), 칸3 한 번 실행(초기 적재·마이그레이션), 칸4 예비 | y 742–848 (h 106) |

고정 영역: 제목 left 56·top 30 / 부제 left 58·top 78 / 색 범례 right 48·top 40 / 각주 left 56·top 872.

- L1 사용자·클라이언트는 실제로 같은 기기 안에 있어도(예: 같은 PC의 브라우저) **항상 경계 밖** L1에 둔다. L1 상자의 세로 위치는 연결되는 L2(없으면 L3) 상자와 같은 높이대로 맞춘다.
- L3 실행 단위가 1개라도 안쪽 계층 정보가 없으면 `container`+`inner` 대신 `box srv` 한 상자로 그린다.
- 진입점(웹 서버 역할)이 실행 단위와 **같은 프로세스**면 L2에 따로 그리지 않는다. L2를 비우고 L1 ↔ L3를 양쪽 화살촉 선 하나로 잇고, 실행 단위 칩에 "화면 파일 제공" 같은 진입 역할을 적는다.

**레인 안 쌓기 (세로)**

| 레인 | 시작 y | 끝 y | 상자 높이 | 최대 개수 |
|---|---|---|---|---|
| L1 | 180 | 690 | 칩 있으면 150, 없으면 122. 간격 50 | 3 |
| L2 | 200 | 690 | 진입 상자는 내용에 맞게(최소 112), 트리거는 112. 간격 ≥ 50(경계가 둘이면 ≥ 30) | 3 |
| L3 | 168 | 690 | 1개면 522(컨테이너+안쪽 계층 가능). n개(2~3)면 `(522 − 40(n−1)) / n`, 간격 40 | 3 |
| L4 | 290 (L3→L5 선이 없으면 168) | 690 | n개면 `(400 − 12(n−1)) / n` (시작 168이면 522 기준), 간격 12. 1~2개면 간격 38. 최소 72(제목 + 1줄). 개요 그림에서만 제목만 둔 최소 50 허용 | 4 |
| L5 | 178 (경계 수와 무관하게 항상) | 2개면 430, 3개면 520 | 최소 96, 간격 20 | 3 (3개면 "연결 읽는 법"은 아래 줄 칸4로) |

- L3 실행 단위 사이 간격 40은 그 사이 연결선의 라벨 자리다.
- 상자 아래 빈 공간은 그대로 둔다. 빈 곳을 채우려고 내용을 늘리지 않는다.
- 칩은 상자마다 2~5개. 공간이 모자라면 줄이고, 뺀 내용은 "질문 없이 정한 점"에 적는다.
- **크기 규칙**: 어느 레인이든 최대 개수를 넘거나, 선 교차를 없앨 수 없으면 한 장에 억지로 넣지 않는다. 먼저 같은 종류를 한 상자로 묶을 수 있는지 본다(예: 알림 채널 2개 → "알림 채널 2종"). 그래도 안 되면 사용자에게 "전체 개요 1장 + 영역별 상세 그림"으로 나눌지 묻는다.
  - 개요: 실행 단위·외부 서비스를 묶은 상자로 그리고, 운영 외 작업은 생략할 수 있다(상세에 둔다). 제목 뒤에 ` · 전체 개요`.
  - 상세: 영역 하나씩(예: 수집·경보 / 조회·보고), 같은 레인 규칙. 제목 뒤에 ` · 상세: {영역}`.

**실행 경계**

- 실행 경계(Docker Compose, Kubernetes 클러스터, 클라우드 계정·VPC, 사용자 PC 등)는 회색 점선 둥근 사각형과 왼쪽 위 라벨(경계 이름)로 그린다. 기본은 L2~L4를 감싸는 x 240–1275, y 140–705.
- **레인 시작 y는 경계 top 기준 상대값**이다(경계가 하나면 top 140이라 위 표의 값이 된다): L2 = top + 60, L3 = top + 28, L4 = top + 150(L3 → L5 선이 있을 때) 또는 top + 28, L4 위 띠 통로 = top + 80 / 105 / 130. 각 레인의 끝 y는 경계 bottom − 15. 경계 밖인 L1·L5는 상대값을 쓰지 않는다(L1은 연결 상대 높이에 맞추고, L5는 항상 178부터).
- 경계가 둘이면 위·아래로 나눈다. 구성 요소가 적은 쪽 경계를 위에 두고 높이를 한 줄(약 180~210)로, 나머지를 아래 경계로 한다(예: 위 140–350, 아래 380–705). 간격 30. 경계마다 위 상대값으로 레인 시작 y를 정한다. 위 경계에서 아래 경계로 가는 선은 두 경계 사이 간격을 수직으로 지난다.
- 같은 클라우드 계정·리전 안의 클러스터와 관리형 서비스는 경계 하나로 묶고 라벨에 둘 다 적는다(예: `AWS 서울 리전 · EKS + 관리형 서비스`). 경계가 셋 이상이 되면 사용자에게 묻는다.
- 경계가 없는 시스템(예: 사용자 PC에서 도는 앱)은 `사용자 PC` 같은 실제 실행 위치를 경계 이름으로 쓴다.
- **운영 외 작업은 항상 아래 줄**에 둔다. 실제로는 경계 안에서 돌더라도(예: 경계 안의 초기화 작업) 아래 줄에 두고, 설명 첫머리에 실제 실행 위치를 적는다.
- **정기 실행 작업**(스케줄러가 깨우는 배치)은 운영 중이므로 아래 줄이 아니라 L3에 두고, 깨우는 쪽(스케줄러)은 L2에 둔다.
- **같은 실행 단위 안의 별도 프로세스**(예: 설정으로 켜는 보조 서버)는 그 실행 단위 컨테이너 안에 안쪽 계층 상자로 따로 그리고 제목 옆 회색 글자로 켜지는 조건을 적는다.

### 4. 연결 표기

- **실선** = 운영 중 호출. **점선(7 5)** = 운영 외 작업(빌드, 한 번 실행, 분리 실행).
- 화살촉 방향(이 규칙만 따른다. 읽기·쓰기 여부로 판단하지 않는다):
  - **양쪽 화살촉**은 사용자 요청이 오가는 경로에만: L1 클라이언트 ↔ L2 진입점 ↔ 요청을 처음 받는 L3 실행 단위.
  - 그 밖의 모든 선은 **연결을 시작하는 쪽 → 받는 쪽** 한쪽 화살촉. 예: 실행 단위 → DB, 실행 단위 → 외부 API, 서비스 → 다른 서비스, 발행자 → 큐, **구독자 → 큐·브로커**(구독도 구독자가 연결을 시작함), 장비 → 브로커(발행), 스케줄러 → 작업, 빌드 → 진입점, 스크립트 → DB.
  - 두 상자가 **각자 연결을 시작**하면(예: A가 B를 프로세스로 띄우고, B가 A의 API를 부름) 선 하나에 양쪽 화살촉을 쓰고 라벨에 두 방향을 ` / `로 적는다(예: `프로세스 시작 / HTTP (fake)`).
- 끝점: 상자 테두리에서 2px 떨어진 곳에서 시작·끝난다(예: 오른쪽 끝 x 222 → 시작 224).
- 경로: 수평·수직 직선과 직각 꺾임만(`M x,y H x2 V y2`). 대각선·곡선 금지.
- **선끼리 교차 금지.** 교차가 생기면 상자의 세로 순서·위치나 진입 높이를 바꾼다. 연결이 많은 상자끼리 같은 높이에 오도록 레인 안 순서를 정한다.
- 선이 지나갈 통로(어떤 선이든 교차를 피하려고 쓸 수 있다):
  - 레인 사이 간격(222–266, 476–540, 902–980, 1250–1320)
  - L4 위 띠(y 205–280): L3 → L5 선은 여기를 지난다. 여러 개면 y 220, 245, 270을 차례로 쓰고, 아래쪽 외부 상자로 가는 선은 1250–1320 간격에서 아래로 꺾는다(먼저 꺾는 선이 오른쪽).
  - 경계 아래 띠(y 712–728): 아래쪽 L3 상자 → L5, L2 → L4·L5(L3를 건너가는 선), 아래 줄 → 위 레인 선이 지난다. 1250–1320 간격이나 L5 오른쪽 끝 x 1540에서 위로 올라간다.
  - 꺾인 선의 구간이 모두 짧아 라벨 자리가 없으면 출발하는 변(오른쪽·위·아래)을 바꿔 라벨을 둘 구간을 만든다.
  - 같은 간격에서 여러 선이 꺾일 때는 서로 교차하지 않는 순서로 꺾는 x를 정한다(아래로 꺾으면 먼저 꺾는 선이 오른쪽, 위로 꺾으면 먼저 꺾는 선이 왼쪽).
- **같은 두 상자 사이에는 선 하나만** 그린다. 용도가 여럿이면 라벨에 ` · `로 나열한다. 서로 다른 상자로 가면 선을 나눈다.
- **조건부 연결**(설정을 켰을 때만 쓰는 경로)도 운영 중 호출이면 실선으로 그리고 라벨 끝에 조건을 괄호로 붙인다(예: `HTTPS · 알림 (prod)`). 받는 상자 설명 첫 줄에도 조건을 적는다.
- **라벨은 모든 선에** 붙인다. 형식은 `프로토콜` 또는 `프로토콜 · 용도`로 짧게(예: `HTTP`, `gRPC`, `SQL`, `함수 호출 (import)`, `발행`, `구독`, `HTTPS · 결제 승인`, `빌드`, `적재`).
- **같은 상자로 들어가는** 선 두 개 이상이 같은 라벨이면 보내는 쪽이나 용도를 앞에 붙여 구분한다. 서로 다른 상자로 가는 선은 같은 라벨을 그대로 쓴다.
- 라벨 위치: 수평선은 선 위(라벨 top = 선 y − 23), 공간이 없으면 선 아래(top = 선 y + 6). 수직선은 선 오른쪽 8~10px, 공간이 없으면 같은 선의 수평 구간에. 꺾인 선은 가장 긴 구간에 한 번만. 겹치면 옮긴다.
- 구조 원칙(예: "클라이언트는 진입점만 부름 / 서비스 사이 비동기 이벤트는 큐를 거침")은 "연결 읽는 법" 아래 `.note`에 2줄 이내로 적는다.

- 렌더 임시 파일을 저장 폴더 밖에 만들면 안 되는 환경이면 `--user-data-dir="$PWD/.chrome-tmp"`를 붙이고 렌더 뒤 그 폴더를 지운다.

4. 렌더한 PNG를 **직접 열어 보고** 모두 확인한다. 하나라도 어기면 고치고 다시 렌더한다.
   - [ ] 라벨이 선·화살촉·상자와 겹치지 않는다(실행 경계 점선 위는 허용 — 라벨 흰 바탕이 가림. 예: L1–L2 사이 라벨)
   - [ ] 글자가 상자 밖으로 넘치거나 잘리지 않는다(각주·부제 포함 한 줄)
   - [ ] 선끼리 교차하지 않는다
   - [ ] 모든 선에 라벨이 있고, 실선·점선·화살촉 방향이 4장과 맞다
   - [ ] 색이 5장의 역할과 맞다(빨간색은 분리 실행에만)
   - [ ] 모든 상자가 3장의 레인 x 범위 안에 있고, 레인 판단 기준과 맞다
   - [ ] 내부 처리 흐름이 들어가 있지 않다
   - [ ] `pdfinfo` 기준 1쪽, 1200 × 675 pts(= 1600×900 px. Chrome 출력의 675.12는 정상)
5. 수정 요청을 받으면 같은 파일을 고치고 세 파일을 모두 다시 만든다.

보여 주는 규칙: 실행 단위 사이 동기 호출(주문 → 결제), 발행자·구독자 모두 → 큐, L4 위 띠(y 220)로 L3 → L5, 경계 아래 띠(y 720)와 x 1540으로 아래쪽 실행 단위 → L5, 라벨 공간이 없을 때 선 아래에 둠(정기 실행), 색 범례 "화면·진입"(게이트웨이)·"데이터"(DB 외 종류 있음).
