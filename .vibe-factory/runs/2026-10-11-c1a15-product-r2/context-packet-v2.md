# 파트장이 승인할 수 있는 지시만 내는 야간 정비 Agent

## 방향 축
- primary_user: 숙련자가 없는 야간·주말 교대에 설비 알람을 혼자 받는 1~3년차 정비 기술자. 설비 앞 태블릿에서 매뉴얼 절과 과거 사례를 근거로 "다음에 무엇을 점검할지"를 한 단계씩 안내받아 결과를 입력하고, 끝나면 정비 보고서를 확정한다. 정비 파트장은 아침에 보고서를 승인해 이력으로 넘기고, Agent가 혼자 지시할 수 있는 범위를 정하는 2차 사용자다.
- problem_framing: 알람은 증상(온도 차 저하, 출력 이탈 등)만 알려 주고, 근본 원인(필터 막힘·팬 열화·설정 오류 등)이나 "실제로는 이상 없음"은 점검해야 가려진다. 숙련자 의존을 "어떤 점검부터 할지 아는 감각"의 부재와, 그 감각의 재료인 과거 정비 기록이 다음 판단에 쓰이지 않는 문제로 정의한다.
- value_mechanism: 알람 해석, 유사 사례 검색, 원인 순위·점검 선택, 매뉴얼 근거 지시, 보고서 작성의 다섯 도구를 LangGraph 루프가 부르며, 정비자 입력마다 원인 순위를 다시 매겨 "짧은 시간에 후보를 가장 많이 가르는 점검"을 다음 지시로 낸다. 순위·선택·권한 판정은 코드가, 근거를 붙인 지시문·메모 해석·보고서는 LLM이 맡고, 근거 번호가 없거나 권한 밖인 지시는 화면에 나가지 않는다.
- knowledge_data_strategy: 고장 라벨을 지운 AI4I 2020 행에서 사전에 정리한 알람 10건으로 시작하고, 이후 라벨 없는 센서 분포로 알람을 생성한다. 가상 매뉴얼 24절은 절 번호와 권한 등급을 붙여 색인하고, 가상 정비 기록 300건은 필드와 서술을 함께 하이브리드 검색하며, 평가 사례 30건은 기록 생성 규칙을 보지 않은 팀원이 따로 쓴다.
- demo_scenario: 02:14 설비 M-07 온도 차 저하 알람에서 Agent가 유사 사례 3건과 매뉴얼 4.3절을 근거로 10분짜리 팬 분해 대신 3분짜리 필터 육안 점검을 먼저 지시하고, 필터 막힘이 확정되면 인용이 달린 보고서가 나온다. 파트장이 승인한 이 보고서는 다음 날 밤 비슷한 알람에서 유사 사례 1순위로 다시 나타난다.
- differentiation: 한 번 검색해 답을 내는 RAG와 달리 정비자 입력을 받을 때마다 다음 점검을 고르므로 점검 소요 분이라는 현장 지표로 체크리스트와 비교할 수 있다. 모든 지시가 매뉴얼 절 번호·이력 ID와 권한 등급에 묶이고, 결과물은 자동 지표뿐 아니라 개발에 참여하지 않은 검토자가 "그대로 승인할 수 있는가"로 판정한다.

## 본문

### 0. 요약
만드는 것은 과제의 기대 결과물 두 가지다. 이상 대응 지원 웹 데모(태블릿 화면 + Agent)와 정비 보고서 샘플. Agent는 알람 1건을 "점검 1개 지시 → 결과 입력 → 순위 갱신"으로 좁혀 원인·조치·보고서까지 잇는다. 원칙은 세 가지다.
1. **한 바퀴 먼저**: 첫 구간은 사전에 정리된 알람 10건으로 알람→점검→보고서 한 바퀴만 완성한다(과제 원문이 허용한 난이도 조절 방식). 평가·생성기는 없다.
2. **근거와 권한 밖의 문장은 내보내지 않는다**: 지시·원인·조치 문장은 매뉴얼 절이나 이력 ID가 붙고, 그 절의 권한 등급이 야간 단독 작업으로 허용된 것만 나간다.
3. **사람이 쓸 수 있는지로 판정한다**: 자동 지표는 작게 두고, 결과물은 개발자가 아닌 검토자가 블라인드로 본다.

### 1. 사용 장면과 과제 기능 대응
| 단계 | 정비자가 보는 것 | 과제 원문 기능 |
|---|---|---|
| ① 알람 | "M-07 · 온도 차 저하 · 02:14", 기준 대비 차이와 방향 | 이상 이벤트 입력·해석, (선택) 알림 |
| ② 근거 | 비슷한 과거 기록 3건(점검 경로·원인·정지 시간) | 유사 사례 검색 |
| ③ 진단 | 원인 후보 순위와 근거 사례 수, 다음 점검 1개와 고른 이유 | 원인 후보 우선순위 |
| ④ 점검 | 절 번호·권한 등급이 달린 지시, 안전 잠금 먼저 | 매뉴얼 기반 절차(근거 제시) |
| ⑤ 입력 | 정상/이상/확인 불가 + 메모 | 정비자 확인(HITL) |
| ⑥ 마감 | 보고서 초안 → 수정·확정 → 파트장 승인 → 이력 반영 | 정비 보고서 초안 |

팀 가정(공개 자료로 확인되지 않음, 화면에도 표시): 신입은 매뉴얼 목차 순으로, 숙련자는 경험과 센서 모양으로 점검 순서를 정한다. 대상은 공구를 쓰는 회전 가공 설비다(AI4I는 설비 종류 미명시).

### 2. Agent 핵심 설계: 다섯 도구와 루프
| 도구 (Function Calling) | 입력 → 출력 | 구현 |
|---|---|---|
| T1 알람 해석 | 센서 5개·Type → 기준 대비 차이·방향, 증상군 | 규칙 코드, LLM 없음 |
| T2 유사 사례 검색 | 설비·증상·센서 차이 방향·이번 세션 소견 → 기록 3건과 ID | 필드 필터 + 서술 BM25·임베딩 하이브리드, 상위 10건을 센서 차이 거리로 재정렬 |
| T3 원인 순위·점검 선택 | 유사 사례 원인 빈도 + 지금까지 소견 → 순위, 다음 점검 | 코드. 점수 = 가르는 후보 비율 ÷ 소요 분, 권한 밖 점검 제외 |
| T4 매뉴얼 근거 지시 | 점검 이름 → 지시문 + 절 번호 | 하위 항목으로 찾고 절 전체를 넘기는 Parent Document 검색 후 LLM 작성 |
| T5 보고서 | 세션 기록 → 보고서 8항목 | LLM 작성 후 필드 검사, 승인 시 이력 색인에 추가 |

```
알람 → T1 → T2 → T3 → T4 → [정비자 입력: HITL 중단점] → 메모 해석(LLM) → T2·T3 갱신
 → 1순위 확정: 조치 절(T4) → T5 / 싼 점검 모두 정상: "이상 없음, 감시" → T5
 / 다음 점검이 권한 밖·점검 소진·모르는 소견: 숙련자 호출 요약 / 그 외: T3로
```
- **근거 검사(코드)**: T4 지시문의 절 번호가 원인–점검 표와 다르거나 검색된 절에 없는 수치가 나오면 1회 재생성, 그래도 다르면 절 원문만 보인다. T5의 원인·조치 문장은 세션 소견·절 번호와 대조해 근거 없는 문장을 지운다.
- **메모 해석**: 애매하면 "필터=이상으로 이해함, 맞습니까?"를 묻고 확인 뒤에만 순위를 바꾼다. 어느 원인과도 맞지 않는 소견이면 순위를 억지로 바꾸지 않고 숙련자 호출로 끝낸다.
- 순위는 확률 모형 대신 유사 사례 원인 빈도에서 시작해 "이상"이면 연결 원인만 남기고 "정상"이면 내린다. 근거 사례가 3건 미만이면 "근거 적음"을 표시한다.
- LLM은 어댑터 뒤에 두어 과정 제공 API로 개발하고 sLLM으로 바꿀 수 있게 한다. 지시·입력·승인은 감사 로그에 남는다.

### 3. 권한 경계: Agent가 혼자 시킬 수 있는 일
매뉴얼 절마다 권한 등급을 붙이고, 판정은 그래프 규칙(코드)이 한다. 등급표는 파트장 역할 팀원이 정하며 화면 설정에서만 바뀐다.
| 등급 | 예 | 처리 |
|---|---|---|
| A 단독 가능 | 잠금 확인, 육안·청음 점검, 필터 교체 | 지시 |
| B 확인 후 | 냉각수 보충, 재가동 | 정비자가 체크리스트 확인 뒤 진행 |
| C 승인 필요 | 설정값 변경, 팬 분해 | 지시하지 않고 파트장 호출 요약 |
| D 범위 밖 | 전기 계통 작업 | 지시하지 않음 |

잠금(1.2절) 확인 전에는 어떤 지시도 나가지 않는다. 이 규칙은 LLM 판단에 맡기지 않으며, 등급 위반 지시가 0건인지를 평가에서 잰다.

| 정비 기록 | 1~9월 알람마다 "센서 방향별 원인 비율표"(팀 가정)로 원인·점검 경로를 뽑고 LLM이 교대 일지체로 서술 | 300건 | 필드·서술만 |
| 평가 사례 카드 | 아래 2 | 30건 | 못 봄 |

1. **입력**: 알람은 라벨 열을 지운 파일에서만 만들고, 임계값은 분포 분위수로 정해 UCI 고장 생성 조건 수치를 쓰지 않는다. 고장 유형 분류 정확도는 생성 규칙을 다시 맞히는 일이라 성능으로 보고하지 않는다.
2. **서로 안 보기**: 평가 담당은 비율표·기록·생성 코드를 보지 않고 10~12월 알람 30건의 센서 값과 매뉴얼만 보고 숨은 원인과 점검별 결과 메모를 쓴다(그래프 밖 원인 3건, "이상 없음" 5건 포함). 데이터 담당도 카드를 보지 않는다.
3. **검색 조건**: 필터는 설비·증상·센서 차이·이번 세션 소견만 허용하고 원인 필터는 없다. 색인에는 1~9월 기록만 들어간다.

`test_separation.py` 하나가 입력 모델의 필드 목록, 색인 ID와 카드 ID 교집합 0, agent 패키지의 `eval/` 임포트 금지를 확인한다.

### 6. 평가 (구간 3, 전체의 11%)
정비자 역할은 카드의 점검별 메모를 돌려주는 조회 함수가 맡아, 메모 해석도 개발자가 쓰지 않은 문장으로 잰다. 비교는 같은 흐름에서 설정만 바꾼다.
| 과제 기능 | 지표 (카드 30건) | 비교 설정 | 목표 |
|---|---|---|---|
| 유사 사례 검색 | 상위 3건에 카드 원인과 같은 사례 포함 | BM25 단독 | 80% 이상 |
| 원인 우선순위 | 첫 응답 Top-3에 카드 원인 포함 | 이력 최빈 원인 | 80% 이상 |
| 점검 순서 | 원인 확정까지 점검 소요 분 | 목차 순 체크리스트 | 20% 이상 단축 |
| 근거·권한 | 인용 절 일치 / 그래프 밖 원인 날조 / 등급 위반 지시 | — | 95% 이상 / 0건 / 0건 |

**블라인드 검토 (5시간)**: 점검 소요 분은 팀이 쓴 매뉴얼 시간에서 나오므로 그것만으로 효과를 주장하지 않는다. 카드 12건마다 Agent 보고서와, 같은 카드로 목차 순 체크리스트를 따라 팀원이 쓴 보고서를 출처를 가리고 섞어 검토자(현직자 멘토링 협조 가정)에게 보인다. 검토자는 건마다 "그대로 승인 / 수정 후 승인 / 반려"와 "이 지시대로 야간 단독 작업이 안전한가"를 매긴다. 목표는 Agent 쪽 승인(수정 포함) 10건 이상, 안전 문제 지적 0건이다.

목표에 못 미쳐도 원인과 함께 발표하며, 수치는 "팀이 만든 가상 세계에서, 생성 규칙을 모르는 사람이 쓴 처음 보는 알람"에 대한 결과라고 밝힌다.

### 7. 데모 장면 (수치는 설계용 예시값)
1. "M-07 · 온도 차 저하 · 02:14". 온도 차 7.6 K(1~9월 하위 2.5% 경계 7.9 K 아래), 회전 1,462 rpm → 냉각 계통 쪽. 유사 기록 3건.
2. 순위: 필터 > 팬 > 냉각수 > 설정. 지시: 잠금(1.2절) → 필터 육안(4.3절, A등급, 3분). 이유: "팬 분해(C등급, 10분)는 승인이 필요하고, 필터 점검이 후보를 둘로 가름".
3. 메모 "기름때 두껍게 낌" → 확인 → 필터 확정 → 교체(4.3.2절, A등급) → 보고서 확정.
4. 다른 건: 필터·냉각수가 정상이고 다음이 팬 분해 → 지시 대신 "파트장 호출" 요약.
5. 아침에 파트장 승인 → 다음 날 밤 M-11 비슷한 알람에서 이 보고서가 유사 사례 1순위로 뜬다.

```
[정비 보고서] M-07 / 온도 차 저하 / 02:14~02:31 / 작성: 야간 정비 김○○
센서 근거: ΔT 7.6 K(경계 7.9 K), 1,462 rpm → 냉각 계통 쪽
점검 경로: 잠금(1.2) → 필터 육안(4.3, 이상: 기름때 두꺼움)
확정 원인: 냉각 필터 막힘(근거 사례 H-0112·H-0347·H-0458)
조치: 필터 교체(4.3.2, A), 재가동(B, 확인 완료) 후 온도 차 경계 이내
정지 시간: 17분 / 미확인: 팬 상태(C등급, 주간 확인 요청)
```

### 8. 기술·한계·맥락
FastAPI, Streamlit, LangGraph(순환·분기·HITL 중단점), SQLite, Chroma+BM25, Pydantic, Function Calling으로 모두 과정 커리큘럼 범위다. 원인 분포·매뉴얼·기록·카드·권한 등급은 가상이고 실데이터 효과는 검증하지 않는다. 실제 매뉴얼과 기록으로 바꾸면 같은 절 색인과 등급표를 다시 만들면 되도록 데이터 계층을 나눴다. 현장 인과관계를 구조화해 LLM이 호출하게 해 환각을 줄인 한화시스템 사례와 숙련자 판단 기준을 데이터화하는 방향(Pack 02)을 정비 진단 한 건 단위로 옮겼고, 권한 등급·승인·감사 로그·sLLM 교체 구조는 AgentOne이 강조하는 거버넌스와 규제 준수(Pack 02)에 맞췄다.

## 3. 시나리오

정상 흐름의 기준은 가이드 M-07(온도 차 저하) 장면, 멈춤의 기준은 M-17 장면이다.

### S1. 알람 받기 (`tech`)
1. 알람 발생기가 알람을 등록하면 서버가 담당자를 정한다(규칙 R9).
2. 담당 정비자 홈의 종 아이콘 숫자가 늘고 알림음이 울린다. 새 알람은 빨간 점, 진행 중은 주황, 완료는 초록.
3. 정비자가 "점검 시작"을 누르면 세션이 열리고 알람 화면(가이드 5쪽)이 보인다.
- 대안: 진행 중 세션은 "이어서 하기"로 다시 연다(세션 상태는 서버에 저장, 앱을 닫아도 유지).
- 대안: 여러 알람이 있으면 홈에서 새 알람부터 처리. 한 정비자가 여러 세션을 열어 둘 수 있으나 한 번에 하나만 활성.

### S2. 진단 보기 (`tech`)
1. 서버가 비슷한 과거 기록을 찾고(R3), 원인 후보 순위를 계산하고(R4), 다음 점검을 고른다(R5).
2. 화면(가이드 6쪽): 원인 후보 순위(% · 근거 n), 다음 점검 1개(등급 배지 · 매뉴얼 절 · 약 n분)와 고른 이유, 비슷한 과거 기록 3건(누르면 전체 기록).
3. 비슷한 기록이 3건 미만이면 "근거 적음" 표시(R6). 지시는 그대로 진행.

### S3. 잠금 확인 → 점검 (`tech`)
1. 잠금(1.2절) 확인 전에는 점검 지시 내용이 가려진다. "잠금 완료"를 누르면 시각이 기록되고 지시가 열린다(R1).
2. 증상군 사전 확인 절(x.2)을 먼저 진행한다.
3. 지시된 점검 하나(가이드 8쪽): 절차 단계, 판정 기준, 매뉴얼 원문 보기, 근거 기록 보기. "점검 n / 최대 m" 표시.
4. 정비자가 결과 버튼(정상·이상·확인 불가) + 메모를 보내면 서버가 해석(R7) → 필요하면 확인 질문(가이드 10쪽) → 순위 갱신(R4) → 다음 단계(R5).
- 대안: "확인 불가" → 순위 그대로, 다른 점검 제안. 같은 점검 확인 불가 2회 → 다른 점검, 대안이 없으면 숙련자 인계.
- 대안: 맞지 않는 소견(R7) → 정비자 확인 후 숙련자 인계(S6).

### S4. 원인 확정 → 조치 → 재가동 (`tech`)
1. 확정형 점검이 "이상"이면 그 원인을 확정하고 조치 절을 보인다(가이드 11쪽).
2. 조치 등급: A는 바로 진행 후 "완료", B는 체크리스트를 모두 확인해야 진행 버튼이 열림, C·D는 지시하지 않고 호출(S5).
3. 재가동(6.1절, B): 체크리스트(주변 공구·이물질 치움, 냉각 커버 고정, 작업자 대피) 확인 후 재가동 버튼이 열림.
4. **[결정 D6]** 재가동 후 화면에 현재 값과 경계를 보여 주고 정비자가 "경계 이내 / 여전히 밖"을 고른다. 현재 값은 시연 각본의 값(없으면 경계 안쪽 기본값, R11).
- "경계 이내" → 보고서(S7). "여전히 밖" → 숙련자 인계(원인 확정 후에도 회복 안 됨).

### S5. 파트장 호출 (`tech` → `lead` → `tech`)
1. 호출 조건(R5)이 되면 지시 대신 "다음 점검은 혼자 진행할 수 없습니다" 화면과 자동 작성 요약(가이드 13쪽: 알람, 지금까지 점검·결과, 남은 후보·확률, 필요한 작업·절·등급, 설비 상태). 정비자가 요약을 고칠 수 있다.
2. "파트장 호출" → 파트장 앱 "처리할 호출"에 올라감. "호출하지 않고 대기"도 가능(세션은 대기 상태).
3. **[결정 D8]** 전달은 앱 안에서만(외부 메신저·문자 없음). 파트장 앱은 주기적으로 조회해 새 호출을 표시한다.
4. 파트장 답:
   - **승인 후 진행** → 정비자 앱에 그 C등급 점검·조치 지시가 열림(호출 기록에 승인자·시각)
   - **주간 처리** → 정비자 앱에 "주간 처리로 결정 · 저부하 감시 운전" 표시, 보고서 "미확인 · 요청"에 해당 작업 기록, 보고서 작성으로 진행
   - **직접 확인** → 정비자 앱에 "파트장 확인 중 · 설비 정지 대기" 표시, 파트장이 처리 결과를 남기면 보고서에 들어감
- D등급(7.1 전기 계통, 7.2 외부 업체)은 "승인 후 진행"이 없다. 파트장 답은 주간 처리 또는 직접 확인.

### S6. 그 밖의 멈춤 (`tech`, 가이드 14쪽)
- **숙련자 인계**(맞지 않는 소견, 점검 소진, 같은 점검 확인 불가 2회 후 대안 없음, 재가동 후 회복 안 됨, LLM·검색 반복 실패): 숙련자 인계 요약 + 점검 경로. **[결정 D19]** 파트장 앱 "처리할 호출"에 유형 "숙련자 인계"로 올라감. 보고서는 확정 원인 "원인 미상"으로 작성.
- **근거 적음**: 표시만(S2).
- **이상 없음 · 감시**: A·B 점검 결과가 모두 정상이고 재가동 후 정비자가 "경계 이내"를 고르면 6.2절로 감시 마감. 보고서 확정 원인 "이상 없음 · 감시".

### S7. 보고서 확정 (`tech`, 가이드 12쪽)
1. 서버가 보고서 8항목을 자동 작성(R10)하고 항목마다 출처(자동·센서·입력·매뉴얼·기록)를 표시한다.
2. 연필 아이콘으로 항목을 고칠 수 있다. 고친 내용은 감사 로그에 남는다.
3. "확정 전 확인": 근거 없는 문장 없음 · 권한 등급 위반 없음 · 필수 8항목 채워짐(R8). 하나라도 실패하면 확정 버튼이 잠긴다.
4. 확정 → 승인 대기. 확정 뒤 정비자는 고칠 수 없다(FAQ: 파트장에게 수정 요청 메모).

### S8. 보고서 검토 (`lead`, 가이드 15~16쪽)
1. 승인 대기 목록: 요약 타일(승인 대기 · 처리할 호출 · 권한 위반), 행마다 설비·알람·확정 원인·작성자·확정 시각·근거 기록 수·근거 적음·권한 위반 수, "검토".
2. 검토 화면: 보고서 내용(근거 사례 번호를 누르면 과거 기록), 결정 3개.
   - **그대로 승인** → 이력에 추가(R12)
   - **[결정 D18] 수정 후 승인** → 파트장이 보고서 항목을 직접 고치고 메모(고친 이유)를 남김 → 고친 문장도 근거 검사(R8) → 통과하면 승인 → 이력에 추가. 고친 항목·전후 값·메모는 감사 로그에.
   - **반려** → 사유 필수 → 작성자에게 돌아감
3. **[결정 D14] 반려 후**: 정비자 앱 "최근 내 보고서"에 반려 · 사유 표시. 정비자는 같은 알람을 "이어서 하기"로 열어 추가 점검을 하거나 보고서 항목만 고친 뒤 다시 확정 → 다시 승인 대기.

### S9. 호출 처리 (`lead`, 가이드 16쪽 아래)
- 호출 목록 → 요약(지금까지 점검 · 남은 후보 · 필요한 작업) → 답(S5의 세 가지, 숙련자 인계는 "주간 숙련자 배정 / 직접 확인") + 처리 메모 → 해당 알람 보고서에 기록.

### S10. 권한 등급 설정 (`lead`, 가이드 17쪽)
- 매뉴얼 절 목록(점검·조치 절)과 현재 등급, 눌러서 A~D로 변경, 변경 기록(누가 · 언제 · 무엇을). 바꾼 즉시 다음 지시부터 적용(진행 중 세션 포함, R13). 등급을 낮출 때(C → B·A) 경고 문구.

### S11. 감사 기록 조회 (`lead`)
- 지시 · 입력 · 확인 질문 답 · 호출 · 승인 · 반려 · 보고서 수정 · 등급 변경을 시간순으로 보고 설비·사용자·기간으로 거른다. **[기본안]** 가이드에 화면이 없으므로 승인 대기 화면과 같은 표 형식으로 설계(VCF G2A의 가이드에 없는 상태).

### S12. 로그인 (`tech`, `lead`)
- **[결정 D9]** 미리 등록한 계정 + ID·비밀번호. 정비자 앱은 정비자 역할만, 파트장 앱은 파트장 역할만 로그인 가능. 회원가입·비밀번호 찾기 없음. 로그인 직후 정비자 앱은 알림음 사용을 위해 화면을 한 번 누르게 함(브라우저 자동 재생 제한).

### S13. 시연 알람 발생 (비UI)
- **[결정 D7]** 시연 각본 파일의 알람을 명령(또는 시연용 버튼)으로 한 건씩 "지금" 발생. 화면 시각은 실제 현재 시각, 센서 값은 각본이 가리키는 데이터 행의 값(R11).

### S14. 평가 실행 (비UI)
- 평가 카드(10~12월 알람 30건, 생성 규칙을 모르는 팀원이 작성)로 정비자 API를 호출하고, 점검마다 카드의 결과·메모를 돌려주어 지표를 계산한다. 평가 모드에서는 이력 색인 추가(R12)를 하지 않는다.

## 4. 규칙 (코드가 판정 — LLM에 맡기지 않음)

### R1. 잠금 선행
- 세션의 첫 단계는 1.2절 잠금 확인. 잠금 기록이 없으면 서버는 점검·조치 지시 내용을 내려주지 않는다(API 수준에서 차단).
- 다른 설비로 세션을 옮기면 잠금을 다시 확인한다.

### R2. 권한 등급
- 지시 가능 여부는 현재 등급표(운영 데이터, 초기값은 매뉴얼 부록 B)로 판정: A 지시, B 체크리스트 확인 후 지시, C·D 지시하지 않음(호출).
- 지시·보고서에 C·D 작업이 "지시"로 나가면 권한 위반으로 센다(목표 0건).

### R3. 비슷한 과거 기록 검색 **[기본안]**
- 대상: 지식 schema의 정비 이력(생성 이력 300건 + 승인된 보고서).
- 필터: 같은 증상군.
- 질의: 증상군 · 알람 값 방향 · 이번 세션의 점검 결과·메모.
- 키워드 검색(BM25, agent 패키지 메모리 색인, 토큰 = 공백 단위 + 한글 2-gram)과 의미 검색(pgvector, 기록 서술 임베딩)을 순위 융합(RRF, k=60)해 상위 10건.
- 상위 10건을 센서 거리로 다시 정렬: 센서 값 5개 + 온도 차·출력을 1~9월 평균·표준편차로 정규화한 유클리드 거리 d, `score = 0.5 × RRF정규화 + 0.5 × (1 − d정규화)`. 유사도 % = score × 100(반올림).
- 화면의 "비슷한 과거 기록 3건" = 상위 3건. 순위 계산(R4)은 상위 10건을 쓴다.

### R4. 원인 후보 순위 **[결정 D4]**
- 후보 집합: 그 증상군 매뉴얼 개요(x.1)의 원인 전부.
- 점수: `점수(c) = α + Σ 유사도(r)` (r = 상위 10건 중 확정 원인이 c인 기록), α = 0.5 **[기본안]**. "근거 n" = 상위 10건 중 원인 c인 기록 수.
- 확률(%) = 점수 ÷ 후보 점수 합 × 100. 합이 100이 되게 반올림 조정.
- 갱신:
  - 확정형 점검 "이상" → 그 원인 확정(100%), 진단 종료 → S4
  - 선별형 점검(3.5, 5.5) "이상" → 그 점검의 원인만 후보로 남김
  - 점검 "정상" → 그 점검의 원인을 후보에서 뺌, 나머지로 다시 100%
  - "확인 불가" → 변경 없음
  - 확인 질문(R7)에 "아니요" → 반영 안 함, 다시 입력
- 결과 입력이 반영될 때마다 다시 계산해 보여 준다.

### R5. 다음 점검 선택과 호출 **[결정 D5]**
1. 잠금 → 사전 확인(x.2)은 점수 없이 항상 먼저.
2. 고를 수 있는 점검: 그 증상군 점검 중 아직 하지 않았고, 확인 불가 2회가 아니며, 연결 원인이 후보에 남아 있고, 현재 등급이 A·B인 것.
3. 점수 = 연결 원인의 현재 확률(%) ÷ 소요 분. 가장 큰 것을 지시. 같으면 절 번호가 앞선 것.
4. 호출 조건(먼저 판정):
   - 1순위 원인을 확인할 점검이 C·D뿐이고 그 확률이 **50% 이상**이면 다른 A·B 점검이 남아 있어도 호출. 50%는 서버 설정 값 `call_threshold`(가이드에 없는 화면은 만들지 않음).
   - 고를 수 있는 A·B 점검이 없고 후보가 남아 있으면 1순위 원인의 C·D 점검으로 호출.
5. 후보가 비면(모두 정상) → 재가동 확인(S4-4) → 경계 이내면 이상 없음 · 감시, 밖이면 숙련자 인계.
6. "이 점검을 고른 이유" 문장: 코드가 만든 사실(확률·소요 분·등급·대안 점검과 그 등급)을 LLM이 한두 문장으로 쓰고 근거 검사(R8)를 거친다. fixture 모드는 템플릿 문장.

**계산 예시(검증용)** — 온도 차 저하, 상위 10건 중 CL-1 2건(유사도 0.96, 0.91), CL-2 1건(0.84), α = 0.5
- 점수: CL-1 2.37 · CL-2 1.34 · CL-3 0.5 · CL-4 0.5 → 확률 50 · 28 · 11 · 11 (%)
- 다음 점검: 4.3 필터(A, 3분) 50/3 = 16.7 · 4.6 설정(A, 4분) 2.8 · 4.5 냉각수(A, 5분) 2.2 · 4.4 팬(C) 제외 → **4.3 지시**
- 4.3 "정상" → CL-1 제외 → CL-2 57.3 · CL-3 21.4 · CL-4 21.4 → 합 100 조정(큰 나머지 순) 57 · 22 · 21 → 1순위 CL-2(57% ≥ 50%)를 확인할 점검은 4.4(C)뿐 → **파트장 호출**(가이드 M-17과 같은 흐름)

### R6. 근거 적음
- 상위 10건 중 R3 score ≥ 0.5인 기록이 3건 미만이면 "근거 적음" **[기본안]**. 표시만 하고 지시는 계속(가이드). 보고서와 파트장 목록에도 표시.

### R7. 메모 해석 **[결정 D11]**
- 판정은 결과 버튼이 기본이다.
- LLM은 (a) 메모가 버튼과 반대 뜻이거나, (b) 버튼 없이 메모만 있거나, (c) 메모가 매뉴얼 후보 원인 밖의 이상 징후일 때만 신호를 낸다. 출력은 구조화: `{interpretation: 정상|이상|불명, conflicts_with_button: bool, out_of_scope_finding: bool, quote: 메모 일부}`.
- (a)(b) → 확인 질문("{점검 대상} 상태를 '{해석}'으로 이해했습니다. 맞습니까?"). "네" → 해석대로, "아니요" → 다시 입력.
- (c) → "후보 원인과 맞지 않는 소견입니다. 숙련자 인계를 권합니다" + 정비자가 인계 또는 계속을 고름.
- 순위 변경·인계는 정비자 확인 뒤에만.
- fixture 모드: 매뉴얼 판정 기준 단어 목록(예: 기름때·막힘·MIN 아래·유격 / 깨끗·정상·이상 없음)으로 같은 신호를 만든다.

### R8. 근거 검사
- 대상: 점검·조치 지시문, "고른 이유", 보고서 원인·조치 문장, 파트장이 고친 문장.
- 규칙(코드): 문장에 붙은 절 번호가 원인–점검 표(매뉴얼 부록 A)·이번 세션 기록과 맞는가, 문장 속 수치가 인용한 절 원문·세션 입력·센서 값에 있는가, 근거 사례 ID가 R3 상위 10건에 있는가.
- 실패 → 1회 다시 작성 → 또 실패 → 절 원문(또는 템플릿 문장)으로 대체하고 "원문으로 대체됨" 표시. 보고서의 근거 없는 문장은 지운다.
- 확정 전 확인 3항목(근거 없는 문장 · 권한 위반 · 필수 항목)이 모두 통과해야 확정·승인 가능.

### R9. 알람 배정 **[결정 D13]**
- 설비 담당표(초기 데이터: M-01~M-20을 정비자에게 나눔)의 담당자에게 배정.
- 담당자가 로그인해 있지 않으면 로그인한 정비자 중 처리 중 알람이 가장 적은 사람(같으면 사용자 ID 순).
- 로그인한 정비자가 없으면 미배정으로 두고 다음 로그인 정비자에게 배정.

### R11. 시연 각본 **[결정 D7, D6, D12]**
- 파일 `data/demo/scenarios.json` **[기본안 경로]**: 알람 10건. 각 건 = `{scenario_id, udi, equipment_id, restart_value_after_fix(선택), restart_value_if_none(선택)}`.
- 10건은 **10~12월 데이터 행**(이력에 쓰지 않은 행)에서 고른다: 온도 차 저하 5, 출력 이탈 2, 공구 마모 2, 토크 과부하 1 **[기본안]**. 각본에는 숨은 원인을 적지 않는다(시연자가 정비자 역할).
- 재가동 후 표시 값: 각본 값, 없으면 경계 안쪽 값(경계 + 여유 10%).
- 알람 화면 추이 그래프: 같은 설비의 알람 행 이전 측정 12회(실제 간격), 제목 "온도 차 추이 · 최근 12회 측정"(증상군마다 해당 값).

### R12. 이력 색인 추가
- 승인(그대로 · 수정 후) 시 보고서를 정비 이력 형식으로 바꿔 지식 schema에 넣고 임베딩·BM25 색인을 갱신. 출처 `approved_report`, 원래 보고서 ID 연결.
- 평가 모드(`eval_mode=true`)에서는 하지 않는다. 평가 카드 알람의 보고서는 이력에 들어가지 않는다.

## 8. LLM과 실행 모드 **[결정 D10]**

- LLM Adapter 뒤에 OpenAI(대화 모델 + `text-embedding-3-small`). 나중에 sLLM으로 교체 가능하게 인터페이스 분리.
- 실행 모드: `fixture`(기본, 키 없이 동작 — 문장은 매뉴얼 원문 템플릿, 메모 해석은 단어 규칙, 임베딩은 녹화본) / `live`(OpenAI 호출). live 실행·키 사용은 사용자 승인 후.
- LLM이 쓰는 곳: 지시문, "고른 이유", 메모 해석(R7), 보고서 문장, 호출·인계 요약 초안. 순위·선택·권한·잠금·근거 검사는 코드.
- **[기본안]** LLM·검색 실패: 해당 문장을 템플릿·원문으로 대체하고 화면에 "원문으로 대체됨" 표시. 같은 세션에서 3회 연속 실패하면 숙련자 인계를 권함.

## 3. 원문이 예시로 든 데이터셋: UCI AI4I 2020 Predictive Maintenance Dataset (공식 설명 요약)

- 실제 예지보전 데이터는 공개가 어려워, 실제 산업 데이터를 반영하도록 만든 **합성(synthetic) 데이터**입니다.
- 10,000행, 결측값 없음, 라이선스 CC BY 4.0. UCI 분류는 multivariate/time-series입니다.
- 14개 컬럼: 식별자(UDI, Product ID), 제품 품질 등급(Type: L/M/H), 운전 입력 5개, 고장 여부 `Machine failure`, 고장 유형 5개(TWF, HDF, PWF, OSF, RNF).
- 운전 입력 5개:
  - `Air temperature [K]`: random walk로 생성, 300 K 주변 표준편차 2 K
  - `Process temperature [K]`: random walk, 표준편차 1 K, 공기 온도 + 10 K
  - `Rotational speed [rpm]`: 2,860 W 출력 기준으로 계산하고 정규분포 잡음을 더함
  - `Torque [Nm]`: 평균 40 Nm, σ 10 Nm, 음수 없음
  - `Tool wear [min]`: 품질 등급 L/M/H에 따라 공정마다 2/3/5분씩 증가
- 품질 등급 비율: L 50%, M 30%, H 20%.
- UCI가 문서화한 고장 유형 생성 조건:
  - TWF(공구 마모 고장): 공구 사용 200~240분 사이 무작위 시점에 공구 교체 또는 고장
  - HDF(방열 고장): 공기·공정 온도 차 < 8.6 K 이고 회전 속도 < 1,380 rpm
  - PWF(전력 고장): 출력(토크 × 각속도)이 3,500 W 미만 또는 9,000 W 초과
  - OSF(과부하 고장): 공구 마모 × 토크가 L 11,000 / M 12,000 / H 13,000 minNm 초과
  - RNF(무작위 고장): 공정 파라미터와 무관하게 0.1% 확률
- 다섯 유형 중 하나라도 참이면 `Machine failure = 1`입니다. UCI는 이 집계 라벨만으로는 어떤 유형 때문에 고장 났는지 알 수 없다고 설명합니다.
- 특정 설비 종류(예: 밀링 머신)를 명시하지 않고 "the machine"으로만 지칭합니다.
- 설비 ID, 시각, 알람 코드, 정비 이력, 정비 매뉴얼 컬럼은 없습니다.

- 이상 탐지 규칙 연동과 자동 알림은 **(선택)** 기능입니다.
- 이상 이벤트를 사전에 정리된 형태로 제공해 난이도를 조절할 수 있습니다.
