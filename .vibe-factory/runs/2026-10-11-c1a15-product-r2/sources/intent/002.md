## 1. 제품 개요

- **[사실]** 숙련자 없는 야간·주말 교대에 설비 알람을 받은 1~3년차 정비자에게, 매뉴얼 절과 과거 정비 기록을 근거로 다음 점검을 한 번에 하나씩 안내하고, 결과 입력마다 원인 후보를 다시 매겨 원인 확정·조치·보고서까지 잇는다. 정비 파트장은 보고서를 승인해 이력으로 넘기고, Agent가 혼자 지시할 수 있는 범위(권한 등급)를 정한다.
- **[사실]** 과제 10 기대 결과물: 이상 대응 지원 웹 데모, 정비 보고서 자동 생성 샘플.
- **[결정 D1]** 화면 구성·버튼·문구 형식·동작 순서는 사용 가이드와 같게 한다. 수치·매뉴얼 절 번호·기록 번호·설비 번호는 `data/`에서 나오는 실제 값을 쓴다(가이드의 7.9 K, 55%, H-0347, 5.2절 같은 예시 값은 그대로 재현하지 않음).

## 3. 시나리오

정상 흐름의 기준은 가이드 M-07(온도 차 저하) 장면, 멈춤의 기준은 M-17 장면이다.

### S1. 알람 받기 (`tech`)
1. 알람 발생기가 알람을 등록하면 서버가 담당자를 정한다(규칙 R9).
2. 담당 정비자 홈의 종 아이콘 숫자가 늘고 알림음이 울린다. 새 알람은 빨간 점, 진행 중은 주황, 완료는 초록.
3. 정비자가 "점검 시작"을 누르면 세션이 열리고 알람 화면(가이드 5쪽)이 보인다.
- 대안: 진행 중 세션은 "이어서 하기"로 다시 연다(세션 상태는 서버에 저장, 앱을 닫아도 유지).
- 대안: 여러 알람이 있으면 홈에서 새 알람부터 처리. 한 정비자가 여러 세션을 열어 둘 수 있으나 한 번에 하나만 활성.

### S2. 진단 보기 (`tech`)
1. 서버가 비슷한 과거 기록을 찾고(R3), 원인 후보 순위를 계산하고(R4), 다음 점검을 고른다(R5).
2. 화면(가이드 6쪽): 원인 후보 순위(% · 근거 n), 다음 점검 1개(등급 배지 · 매뉴얼 절 · 약 n분)와 고른 이유, 비슷한 과거 기록 3건(누르면 전체 기록).
3. 비슷한 기록이 3건 미만이면 "근거 적음" 표시(R6). 지시는 그대로 진행.

### S3. 잠금 확인 → 점검 (`tech`)
1. 잠금(1.2절) 확인 전에는 점검 지시 내용이 가려진다. "잠금 완료"를 누르면 시각이 기록되고 지시가 열린다(R1).
2. 증상군 사전 확인 절(x.2)을 먼저 진행한다.
3. 지시된 점검 하나(가이드 8쪽): 절차 단계, 판정 기준, 매뉴얼 원문 보기, 근거 기록 보기. "점검 n / 최대 m" 표시.
4. 정비자가 결과 버튼(정상·이상·확인 불가) + 메모를 보내면 서버가 해석(R7) → 필요하면 확인 질문(가이드 10쪽) → 순위 갱신(R4) → 다음 단계(R5).
- 대안: "확인 불가" → 순위 그대로, 다른 점검 제안. 같은 점검 확인 불가 2회 → 다른 점검, 대안이 없으면 숙련자 인계.
- 대안: 맞지 않는 소견(R7) → 정비자 확인 후 숙련자 인계(S6).

### S4. 원인 확정 → 조치 → 재가동 (`tech`)
1. 확정형 점검이 "이상"이면 그 원인을 확정하고 조치 절을 보인다(가이드 11쪽).
2. 조치 등급: A는 바로 진행 후 "완료", B는 체크리스트를 모두 확인해야 진행 버튼이 열림, C·D는 지시하지 않고 호출(S5).
3. 재가동(6.1절, B): 체크리스트(주변 공구·이물질 치움, 냉각 커버 고정, 작업자 대피) 확인 후 재가동 버튼이 열림.
4. **[결정 D6]** 재가동 후 화면에 현재 값과 경계를 보여 주고 정비자가 "경계 이내 / 여전히 밖"을 고른다. 현재 값은 시연 각본의 값(없으면 경계 안쪽 기본값, R11).
- "경계 이내" → 보고서(S7). "여전히 밖" → 숙련자 인계(원인 확정 후에도 회복 안 됨).

### S5. 파트장 호출 (`tech` → `lead` → `tech`)
1. 호출 조건(R5)이 되면 지시 대신 "다음 점검은 혼자 진행할 수 없습니다" 화면과 자동 작성 요약(가이드 13쪽: 알람, 지금까지 점검·결과, 남은 후보·확률, 필요한 작업·절·등급, 설비 상태). 정비자가 요약을 고칠 수 있다.
2. "파트장 호출" → 파트장 앱 "처리할 호출"에 올라감. "호출하지 않고 대기"도 가능(세션은 대기 상태).
3. **[결정 D8]** 전달은 앱 안에서만(외부 메신저·문자 없음). 파트장 앱은 주기적으로 조회해 새 호출을 표시한다.
4. 파트장 답:
   - **승인 후 진행** → 정비자 앱에 그 C등급 점검·조치 지시가 열림(호출 기록에 승인자·시각)
   - **주간 처리** → 정비자 앱에 "주간 처리로 결정 · 저부하 감시 운전" 표시, 보고서 "미확인 · 요청"에 해당 작업 기록, 보고서 작성으로 진행
   - **직접 확인** → 정비자 앱에 "파트장 확인 중 · 설비 정지 대기" 표시, 파트장이 처리 결과를 남기면 보고서에 들어감
- D등급(7.1 전기 계통, 7.2 외부 업체)은 "승인 후 진행"이 없다. 파트장 답은 주간 처리 또는 직접 확인.

### S6. 그 밖의 멈춤 (`tech`, 가이드 14쪽)
- **숙련자 인계**(맞지 않는 소견, 점검 소진, 같은 점검 확인 불가 2회 후 대안 없음, 재가동 후 회복 안 됨, LLM·검색 반복 실패): 숙련자 인계 요약 + 점검 경로. **[결정 D19]** 파트장 앱 "처리할 호출"에 유형 "숙련자 인계"로 올라감. 보고서는 확정 원인 "원인 미상"으로 작성.
- **근거 적음**: 표시만(S2).
- **이상 없음 · 감시**: A·B 점검 결과가 모두 정상이고 재가동 후 정비자가 "경계 이내"를 고르면 6.2절로 감시 마감. 보고서 확정 원인 "이상 없음 · 감시".

### S7. 보고서 확정 (`tech`, 가이드 12쪽)
1. 서버가 보고서 8항목을 자동 작성(R10)하고 항목마다 출처(자동·센서·입력·매뉴얼·기록)를 표시한다.
2. 연필 아이콘으로 항목을 고칠 수 있다. 고친 내용은 감사 로그에 남는다.
3. "확정 전 확인": 근거 없는 문장 없음 · 권한 등급 위반 없음 · 필수 8항목 채워짐(R8). 하나라도 실패하면 확정 버튼이 잠긴다.
4. 확정 → 승인 대기. 확정 뒤 정비자는 고칠 수 없다(FAQ: 파트장에게 수정 요청 메모).

### S8. 보고서 검토 (`lead`, 가이드 15~16쪽)
1. 승인 대기 목록: 요약 타일(승인 대기 · 처리할 호출 · 권한 위반), 행마다 설비·알람·확정 원인·작성자·확정 시각·근거 기록 수·근거 적음·권한 위반 수, "검토".
2. 검토 화면: 보고서 내용(근거 사례 번호를 누르면 과거 기록), 결정 3개.
   - **그대로 승인** → 이력에 추가(R12)
   - **[결정 D18] 수정 후 승인** → 파트장이 보고서 항목을 직접 고치고 메모(고친 이유)를 남김 → 고친 문장도 근거 검사(R8) → 통과하면 승인 → 이력에 추가. 고친 항목·전후 값·메모는 감사 로그에.
   - **반려** → 사유 필수 → 작성자에게 돌아감
3. **[결정 D14] 반려 후**: 정비자 앱 "최근 내 보고서"에 반려 · 사유 표시. 정비자는 같은 알람을 "이어서 하기"로 열어 추가 점검을 하거나 보고서 항목만 고친 뒤 다시 확정 → 다시 승인 대기.

### S9. 호출 처리 (`lead`, 가이드 16쪽 아래)
- 호출 목록 → 요약(지금까지 점검 · 남은 후보 · 필요한 작업) → 답(S5의 세 가지, 숙련자 인계는 "주간 숙련자 배정 / 직접 확인") + 처리 메모 → 해당 알람 보고서에 기록.

### S10. 권한 등급 설정 (`lead`, 가이드 17쪽)
- 매뉴얼 절 목록(점검·조치 절)과 현재 등급, 눌러서 A~D로 변경, 변경 기록(누가 · 언제 · 무엇을). 바꾼 즉시 다음 지시부터 적용(진행 중 세션 포함, R13). 등급을 낮출 때(C → B·A) 경고 문구.

### S11. 감사 기록 조회 (`lead`)
- 지시 · 입력 · 확인 질문 답 · 호출 · 승인 · 반려 · 보고서 수정 · 등급 변경을 시간순으로 보고 설비·사용자·기간으로 거른다. **[기본안]** 가이드에 화면이 없으므로 승인 대기 화면과 같은 표 형식으로 설계(VCF G2A의 가이드에 없는 상태).

### S12. 로그인 (`tech`, `lead`)
- **[결정 D9]** 미리 등록한 계정 + ID·비밀번호. 정비자 앱은 정비자 역할만, 파트장 앱은 파트장 역할만 로그인 가능. 회원가입·비밀번호 찾기 없음. 로그인 직후 정비자 앱은 알림음 사용을 위해 화면을 한 번 누르게 함(브라우저 자동 재생 제한).

### S13. 시연 알람 발생 (비UI)
- **[결정 D7]** 시연 각본 파일의 알람을 명령(또는 시연용 버튼)으로 한 건씩 "지금" 발생. 화면 시각은 실제 현재 시각, 센서 값은 각본이 가리키는 데이터 행의 값(R11).

### S14. 평가 실행 (비UI)
- 평가 카드(10~12월 알람 30건, 생성 규칙을 모르는 팀원이 작성)로 정비자 API를 호출하고, 점검마다 카드의 결과·메모를 돌려주어 지표를 계산한다. 평가 모드에서는 이력 색인 추가(R12)를 하지 않는다.

## 4. 규칙 (코드가 판정 — LLM에 맡기지 않음)

### R1. 잠금 선행
- 세션의 첫 단계는 1.2절 잠금 확인. 잠금 기록이 없으면 서버는 점검·조치 지시 내용을 내려주지 않는다(API 수준에서 차단).
- 다른 설비로 세션을 옮기면 잠금을 다시 확인한다.

### R2. 권한 등급
- 지시 가능 여부는 현재 등급표(운영 데이터, 초기값은 매뉴얼 부록 B)로 판정: A 지시, B 체크리스트 확인 후 지시, C·D 지시하지 않음(호출).
- 지시·보고서에 C·D 작업이 "지시"로 나가면 권한 위반으로 센다(목표 0건).

### R3. 비슷한 과거 기록 검색 **[기본안]**
- 대상: 지식 schema의 정비 이력(생성 이력 300건 + 승인된 보고서).
- 필터: 같은 증상군.
- 질의: 증상군 · 알람 값 방향 · 이번 세션의 점검 결과·메모.
- 키워드 검색(BM25, agent 패키지 메모리 색인, 토큰 = 공백 단위 + 한글 2-gram)과 의미 검색(pgvector, 기록 서술 임베딩)을 순위 융합(RRF, k=60)해 상위 10건.
- 상위 10건을 센서 거리로 다시 정렬: 센서 값 5개 + 온도 차·출력을 1~9월 평균·표준편차로 정규화한 유클리드 거리 d, `score = 0.5 × RRF정규화 + 0.5 × (1 − d정규화)`. 유사도 % = score × 100(반올림).
- 화면의 "비슷한 과거 기록 3건" = 상위 3건. 순위 계산(R4)은 상위 10건을 쓴다.

### R4. 원인 후보 순위 **[결정 D4]**
- 후보 집합: 그 증상군 매뉴얼 개요(x.1)의 원인 전부.
- 점수: `점수(c) = α + Σ 유사도(r)` (r = 상위 10건 중 확정 원인이 c인 기록), α = 0.5 **[기본안]**. "근거 n" = 상위 10건 중 원인 c인 기록 수.
- 확률(%) = 점수 ÷ 후보 점수 합 × 100. 합이 100이 되게 반올림 조정.
- 갱신:
  - 확정형 점검 "이상" → 그 원인 확정(100%), 진단 종료 → S4
  - 선별형 점검(3.5, 5.5) "이상" → 그 점검의 원인만 후보로 남김
  - 점검 "정상" → 그 점검의 원인을 후보에서 뺌, 나머지로 다시 100%
  - "확인 불가" → 변경 없음
  - 확인 질문(R7)에 "아니요" → 반영 안 함, 다시 입력
- 결과 입력이 반영될 때마다 다시 계산해 보여 준다.

### R5. 다음 점검 선택과 호출 **[결정 D5]**
1. 잠금 → 사전 확인(x.2)은 점수 없이 항상 먼저.
2. 고를 수 있는 점검: 그 증상군 점검 중 아직 하지 않았고, 확인 불가 2회가 아니며, 연결 원인이 후보에 남아 있고, 현재 등급이 A·B인 것.
3. 점수 = 연결 원인의 현재 확률(%) ÷ 소요 분. 가장 큰 것을 지시. 같으면 절 번호가 앞선 것.
4. 호출 조건(먼저 판정):
   - 1순위 원인을 확인할 점검이 C·D뿐이고 그 확률이 **50% 이상**이면 다른 A·B 점검이 남아 있어도 호출. 50%는 서버 설정 값 `call_threshold`(가이드에 없는 화면은 만들지 않음).
   - 고를 수 있는 A·B 점검이 없고 후보가 남아 있으면 1순위 원인의 C·D 점검으로 호출.
5. 후보가 비면(모두 정상) → 재가동 확인(S4-4) → 경계 이내면 이상 없음 · 감시, 밖이면 숙련자 인계.
6. "이 점검을 고른 이유" 문장: 코드가 만든 사실(확률·소요 분·등급·대안 점검과 그 등급)을 LLM이 한두 문장으로 쓰고 근거 검사(R8)를 거친다. fixture 모드는 템플릿 문장.

**계산 예시(검증용)** — 온도 차 저하, 상위 10건 중 CL-1 2건(유사도 0.96, 0.91), CL-2 1건(0.84), α = 0.5
- 점수: CL-1 2.37 · CL-2 1.34 · CL-3 0.5 · CL-4 0.5 → 확률 50 · 28 · 11 · 11 (%)
- 다음 점검: 4.3 필터(A, 3분) 50/3 = 16.7 · 4.6 설정(A, 4분) 2.8 · 4.5 냉각수(A, 5분) 2.2 · 4.4 팬(C) 제외 → **4.3 지시**
- 4.3 "정상" → CL-1 제외 → CL-2 57.3 · CL-3 21.4 · CL-4 21.4 → 합 100 조정(큰 나머지 순) 57 · 22 · 21 → 1순위 CL-2(57% ≥ 50%)를 확인할 점검은 4.4(C)뿐 → **파트장 호출**(가이드 M-17과 같은 흐름)

### R6. 근거 적음
- 상위 10건 중 R3 score ≥ 0.5인 기록이 3건 미만이면 "근거 적음" **[기본안]**. 표시만 하고 지시는 계속(가이드). 보고서와 파트장 목록에도 표시.

### R7. 메모 해석 **[결정 D11]**
- 판정은 결과 버튼이 기본이다.
- LLM은 (a) 메모가 버튼과 반대 뜻이거나, (b) 버튼 없이 메모만 있거나, (c) 메모가 매뉴얼 후보 원인 밖의 이상 징후일 때만 신호를 낸다. 출력은 구조화: `{interpretation: 정상|이상|불명, conflicts_with_button: bool, out_of_scope_finding: bool, quote: 메모 일부}`.
- (a)(b) → 확인 질문("{점검 대상} 상태를 '{해석}'으로 이해했습니다. 맞습니까?"). "네" → 해석대로, "아니요" → 다시 입력.
- (c) → "후보 원인과 맞지 않는 소견입니다. 숙련자 인계를 권합니다" + 정비자가 인계 또는 계속을 고름.
- 순위 변경·인계는 정비자 확인 뒤에만.
- fixture 모드: 매뉴얼 판정 기준 단어 목록(예: 기름때·막힘·MIN 아래·유격 / 깨끗·정상·이상 없음)으로 같은 신호를 만든다.

### R8. 근거 검사
- 대상: 점검·조치 지시문, "고른 이유", 보고서 원인·조치 문장, 파트장이 고친 문장.
- 규칙(코드): 문장에 붙은 절 번호가 원인–점검 표(매뉴얼 부록 A)·이번 세션 기록과 맞는가, 문장 속 수치가 인용한 절 원문·세션 입력·센서 값에 있는가, 근거 사례 ID가 R3 상위 10건에 있는가.
- 실패 → 1회 다시 작성 → 또 실패 → 절 원문(또는 템플릿 문장)으로 대체하고 "원문으로 대체됨" 표시. 보고서의 근거 없는 문장은 지운다.
- 확정 전 확인 3항목(근거 없는 문장 · 권한 위반 · 필수 항목)이 모두 통과해야 확정·승인 가능.

### R9. 알람 배정 **[결정 D13]**
- 설비 담당표(초기 데이터: M-01~M-20을 정비자에게 나눔)의 담당자에게 배정.
- 담당자가 로그인해 있지 않으면 로그인한 정비자 중 처리 중 알람이 가장 적은 사람(같으면 사용자 ID 순).
- 로그인한 정비자가 없으면 미배정으로 두고 다음 로그인 정비자에게 배정.

### R11. 시연 각본 **[결정 D7, D6, D12]**
- 파일 `data/demo/scenarios.json` **[기본안 경로]**: 알람 10건. 각 건 = `{scenario_id, udi, equipment_id, restart_value_after_fix(선택), restart_value_if_none(선택)}`.
- 10건은 **10~12월 데이터 행**(이력에 쓰지 않은 행)에서 고른다: 온도 차 저하 5, 출력 이탈 2, 공구 마모 2, 토크 과부하 1 **[기본안]**. 각본에는 숨은 원인을 적지 않는다(시연자가 정비자 역할).
- 재가동 후 표시 값: 각본 값, 없으면 경계 안쪽 값(경계 + 여유 10%).
- 알람 화면 추이 그래프: 같은 설비의 알람 행 이전 측정 12회(실제 간격), 제목 "온도 차 추이 · 최근 12회 측정"(증상군마다 해당 값).

### R12. 이력 색인 추가
- 승인(그대로 · 수정 후) 시 보고서를 정비 이력 형식으로 바꿔 지식 schema에 넣고 임베딩·BM25 색인을 갱신. 출처 `approved_report`, 원래 보고서 ID 연결.
- 평가 모드(`eval_mode=true`)에서는 하지 않는다. 평가 카드 알람의 보고서는 이력에 들어가지 않는다.

### R13. 등급 변경 적용 **[기본안]**
- 저장 즉시 다음 지시 판정부터 적용(진행 중 세션 포함). 이미 열린 지시는 그대로 두고 다음 판정에서 반영.

## 8. LLM과 실행 모드 **[결정 D10]**

- LLM Adapter 뒤에 OpenAI(대화 모델 + `text-embedding-3-small`). 나중에 sLLM으로 교체 가능하게 인터페이스 분리.
- 실행 모드: `fixture`(기본, 키 없이 동작 — 문장은 매뉴얼 원문 템플릿, 메모 해석은 단어 규칙, 임베딩은 녹화본) / `live`(OpenAI 호출). live 실행·키 사용은 사용자 승인 후.
- LLM이 쓰는 곳: 지시문, "고른 이유", 메모 해석(R7), 보고서 문장, 호출·인계 요약 초안. 순위·선택·권한·잠금·근거 검사는 코드.
- **[기본안]** LLM·검색 실패: 해당 문장을 템플릿·원문으로 대체하고 화면에 "원문으로 대체됨" 표시. 같은 세션에서 3회 연속 실패하면 숙련자 인계를 권함.

## 9. 아키텍처 결정 (PBC 입력)

- 화면: 정비자 앱(태블릿) · 파트장 앱(PC) — 각각 React + TypeScript + Vite, 공통 UI 패키지(상단 바 · 등급 배지 · 기록 카드 · API 클라이언트, OpenAPI에서 타입 생성). **[결정 D3]**
- 웹 서버: nginx 하나가 두 앱 파일 제공 + `/api` 중계.
- API 서버: FastAPI 계층이 agent 패키지(LangGraph 그래프 HITL · 도구·코드 규칙 · 검색 BM25 메모리 색인 + pgvector · LLM Adapter · DB 접근)를 import.
- DB: **PostgreSQL 1개, schema 2개**(`ops`, `knowledge` + pgvector). **[결정 D2]** 아키텍처 그림의 DB 상자 2개는 "같은 인스턴스의 schema"로 표기를 고친다.
- 알람 발생기, 데이터 적재 스크립트(매뉴얼·이력·임베딩·초기 등급표·계정·설비 담당표), 평가 실행기.
- Docker Compose로 실행. 템플릿은 쓰지 않고 직접 구성. **[결정 D15]**

## 10. 수용 기준 (관찰 가능한 판정)
