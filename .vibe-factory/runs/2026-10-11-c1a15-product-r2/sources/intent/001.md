# 파트장이 승인할 수 있는 지시만 내는 야간 정비 Agent

## 방향 축
- primary_user: 숙련자가 없는 야간·주말 교대에 설비 알람을 혼자 받는 1~3년차 정비 기술자. 설비 앞 태블릿에서 매뉴얼 절과 과거 사례를 근거로 "다음에 무엇을 점검할지"를 한 단계씩 안내받아 결과를 입력하고, 끝나면 정비 보고서를 확정한다. 정비 파트장은 아침에 보고서를 승인해 이력으로 넘기고, Agent가 혼자 지시할 수 있는 범위를 정하는 2차 사용자다.
- problem_framing: 알람은 증상(온도 차 저하, 출력 이탈 등)만 알려 주고, 근본 원인(필터 막힘·팬 열화·설정 오류 등)이나 "실제로는 이상 없음"은 점검해야 가려진다. 숙련자 의존을 "어떤 점검부터 할지 아는 감각"의 부재와, 그 감각의 재료인 과거 정비 기록이 다음 판단에 쓰이지 않는 문제로 정의한다.
- value_mechanism: 알람 해석, 유사 사례 검색, 원인 순위·점검 선택, 매뉴얼 근거 지시, 보고서 작성의 다섯 도구를 LangGraph 루프가 부르며, 정비자 입력마다 원인 순위를 다시 매겨 "짧은 시간에 후보를 가장 많이 가르는 점검"을 다음 지시로 낸다. 순위·선택·권한 판정은 코드가, 근거를 붙인 지시문·메모 해석·보고서는 LLM이 맡고, 근거 번호가 없거나 권한 밖인 지시는 화면에 나가지 않는다.
- knowledge_data_strategy: 고장 라벨을 지운 AI4I 2020 행에서 사전에 정리한 알람 10건으로 시작하고, 이후 라벨 없는 센서 분포로 알람을 생성한다. 가상 매뉴얼 24절은 절 번호와 권한 등급을 붙여 색인하고, 가상 정비 기록 300건은 필드와 서술을 함께 하이브리드 검색하며, 평가 사례 30건은 기록 생성 규칙을 보지 않은 팀원이 따로 쓴다.
- demo_scenario: 02:14 설비 M-07 온도 차 저하 알람에서 Agent가 유사 사례 3건과 매뉴얼 4.3절을 근거로 10분짜리 팬 분해 대신 3분짜리 필터 육안 점검을 먼저 지시하고, 필터 막힘이 확정되면 인용이 달린 보고서가 나온다. 파트장이 승인한 이 보고서는 다음 날 밤 비슷한 알람에서 유사 사례 1순위로 다시 나타난다.
- differentiation: 한 번 검색해 답을 내는 RAG와 달리 정비자 입력을 받을 때마다 다음 점검을 고르므로 점검 소요 분이라는 현장 지표로 체크리스트와 비교할 수 있다. 모든 지시가 매뉴얼 절 번호·이력 ID와 권한 등급에 묶이고, 결과물은 자동 지표뿐 아니라 개발에 참여하지 않은 검토자가 "그대로 승인할 수 있는가"로 판정한다.

## 본문

### 0. 요약
만드는 것은 과제의 기대 결과물 두 가지다. 이상 대응 지원 웹 데모(태블릿 화면 + Agent)와 정비 보고서 샘플. Agent는 알람 1건을 "점검 1개 지시 → 결과 입력 → 순위 갱신"으로 좁혀 원인·조치·보고서까지 잇는다. 원칙은 세 가지다.
1. **한 바퀴 먼저**: 첫 구간은 사전에 정리된 알람 10건으로 알람→점검→보고서 한 바퀴만 완성한다(과제 원문이 허용한 난이도 조절 방식). 평가·생성기는 없다.
2. **근거와 권한 밖의 문장은 내보내지 않는다**: 지시·원인·조치 문장은 매뉴얼 절이나 이력 ID가 붙고, 그 절의 권한 등급이 야간 단독 작업으로 허용된 것만 나간다.
3. **사람이 쓸 수 있는지로 판정한다**: 자동 지표는 작게 두고, 결과물은 개발자가 아닌 검토자가 블라인드로 본다.

### 1. 사용 장면과 과제 기능 대응
| 단계 | 정비자가 보는 것 | 과제 원문 기능 |
|---|---|---|
| ① 알람 | "M-07 · 온도 차 저하 · 02:14", 기준 대비 차이와 방향 | 이상 이벤트 입력·해석, (선택) 알림 |
| ② 근거 | 비슷한 과거 기록 3건(점검 경로·원인·정지 시간) | 유사 사례 검색 |
| ③ 진단 | 원인 후보 순위와 근거 사례 수, 다음 점검 1개와 고른 이유 | 원인 후보 우선순위 |
| ④ 점검 | 절 번호·권한 등급이 달린 지시, 안전 잠금 먼저 | 매뉴얼 기반 절차(근거 제시) |
| ⑤ 입력 | 정상/이상/확인 불가 + 메모 | 정비자 확인(HITL) |
| ⑥ 마감 | 보고서 초안 → 수정·확정 → 파트장 승인 → 이력 반영 | 정비 보고서 초안 |

팀 가정(공개 자료로 확인되지 않음, 화면에도 표시): 신입은 매뉴얼 목차 순으로, 숙련자는 경험과 센서 모양으로 점검 순서를 정한다. 대상은 공구를 쓰는 회전 가공 설비다(AI4I는 설비 종류 미명시).

### 2. Agent 핵심 설계: 다섯 도구와 루프
| 도구 (Function Calling) | 입력 → 출력 | 구현 |
|---|---|---|
| T1 알람 해석 | 센서 5개·Type → 기준 대비 차이·방향, 증상군 | 규칙 코드, LLM 없음 |
| T2 유사 사례 검색 | 설비·증상·센서 차이 방향·이번 세션 소견 → 기록 3건과 ID | 필드 필터 + 서술 BM25·임베딩 하이브리드, 상위 10건을 센서 차이 거리로 재정렬 |
| T3 원인 순위·점검 선택 | 유사 사례 원인 빈도 + 지금까지 소견 → 순위, 다음 점검 | 코드. 점수 = 가르는 후보 비율 ÷ 소요 분, 권한 밖 점검 제외 |
| T4 매뉴얼 근거 지시 | 점검 이름 → 지시문 + 절 번호 | 하위 항목으로 찾고 절 전체를 넘기는 Parent Document 검색 후 LLM 작성 |
| T5 보고서 | 세션 기록 → 보고서 8항목 | LLM 작성 후 필드 검사, 승인 시 이력 색인에 추가 |

```
알람 → T1 → T2 → T3 → T4 → [정비자 입력: HITL 중단점] → 메모 해석(LLM) → T2·T3 갱신
 → 1순위 확정: 조치 절(T4) → T5 / 싼 점검 모두 정상: "이상 없음, 감시" → T5
 / 다음 점검이 권한 밖·점검 소진·모르는 소견: 숙련자 호출 요약 / 그 외: T3로
```
- **근거 검사(코드)**: T4 지시문의 절 번호가 원인–점검 표와 다르거나 검색된 절에 없는 수치가 나오면 1회 재생성, 그래도 다르면 절 원문만 보인다. T5의 원인·조치 문장은 세션 소견·절 번호와 대조해 근거 없는 문장을 지운다.
- **메모 해석**: 애매하면 "필터=이상으로 이해함, 맞습니까?"를 묻고 확인 뒤에만 순위를 바꾼다. 어느 원인과도 맞지 않는 소견이면 순위를 억지로 바꾸지 않고 숙련자 호출로 끝낸다.
- 순위는 확률 모형 대신 유사 사례 원인 빈도에서 시작해 "이상"이면 연결 원인만 남기고 "정상"이면 내린다. 근거 사례가 3건 미만이면 "근거 적음"을 표시한다.
- LLM은 어댑터 뒤에 두어 과정 제공 API로 개발하고 sLLM으로 바꿀 수 있게 한다. 지시·입력·승인은 감사 로그에 남는다.

### 3. 권한 경계: Agent가 혼자 시킬 수 있는 일
매뉴얼 절마다 권한 등급을 붙이고, 판정은 그래프 규칙(코드)이 한다. 등급표는 파트장 역할 팀원이 정하며 화면 설정에서만 바뀐다.
| 등급 | 예 | 처리 |
|---|---|---|
| A 단독 가능 | 잠금 확인, 육안·청음 점검, 필터 교체 | 지시 |
| B 확인 후 | 냉각수 보충, 재가동 | 정비자가 체크리스트 확인 뒤 진행 |
| C 승인 필요 | 설정값 변경, 팬 분해 | 지시하지 않고 파트장 호출 요약 |
| D 범위 밖 | 전기 계통 작업 | 지시하지 않음 |

잠금(1.2절) 확인 전에는 어떤 지시도 나가지 않는다. 이 규칙은 LLM 판단에 맡기지 않으며, 등급 위반 지시가 0건인지를 평가에서 잰다.

### 4. 지식·데이터와 정답 분리
| 자산 | 만드는 방법 | 규모 | Agent 접근 |
|---|---|---|---|
| 정리된 알람 (구간 1) | 라벨 6열을 지운 AI4I 행 중 온도 차가 낮은 행 10개에 설비·시각을 붙인 표 | 10건 | 봄 |
| 생성 알람 (구간 2) | 라벨 지운 파일을 가상 설비 20대·12개월에 고정 시드로 배치, 1~9월 분포 상·하위 2.5%를 넘으면 알람 | 설계 추정 약 800건 | 봄 |
| 매뉴얼 | 4개 증상군 × 6절. 절마다 점검 방법·판정 기준·조치·소요 분·권한 등급 | 24절 | 봄 |
| 원인–점검 표 | 매뉴얼 작성자가 원인 12 × 점검 16 연결과 절 번호 정리 | 1장 | 봄 |
| 정비 기록 | 1~9월 알람마다 "센서 방향별 원인 비율표"(팀 가정)로 원인·점검 경로를 뽑고 LLM이 교대 일지체로 서술 | 300건 | 필드·서술만 |
| 평가 사례 카드 | 아래 2 | 30건 | 못 봄 |

1. **입력**: 알람은 라벨 열을 지운 파일에서만 만들고, 임계값은 분포 분위수로 정해 UCI 고장 생성 조건 수치를 쓰지 않는다. 고장 유형 분류 정확도는 생성 규칙을 다시 맞히는 일이라 성능으로 보고하지 않는다.
2. **서로 안 보기**: 평가 담당은 비율표·기록·생성 코드를 보지 않고 10~12월 알람 30건의 센서 값과 매뉴얼만 보고 숨은 원인과 점검별 결과 메모를 쓴다(그래프 밖 원인 3건, "이상 없음" 5건 포함). 데이터 담당도 카드를 보지 않는다.
3. **검색 조건**: 필터는 설비·증상·센서 차이·이번 세션 소견만 허용하고 원인 필터는 없다. 색인에는 1~9월 기록만 들어간다.

`test_separation.py` 하나가 입력 모델의 필드 목록, 색인 ID와 카드 ID 교집합 0, agent 패키지의 `eval/` 임포트 금지를 확인한다.

### 5. 범위와 완성 순서 (5인 × 80시간 = 400시간 가정)
| 구간 | 만드는 것 | 완료 조건 | 시간 |
|---|---|---|---|
| 1 얇은 완주 | 온도 차 저하 1개 증상, 알람 10건, 손 기록 20건, 매뉴얼 6절, T1~T5 최소판(BM25), 화면 1장 | 알람 10건이 모두 보고서까지 돈다 | 100h |
| 2 넓히기 | 4개 증상군, 알람 생성, 기록 300건, 하이브리드 검색, 근거·권한 검사, 승인→색인, 카드 30건(병행) | 데모 5장면이 끊김 없이 돈다 | 150h |
| 3 재기 | 카드 30건 실행, 블라인드 검토, 오류 상위 5건 수정 | 6절 표 채움 | 45h |
| 4 마감 | 보고서 샘플 12건, Docker Compose, 리허설 2회 | 발표 | 55h + 버퍼 50h |

- **하지 않음**: 실시간 스트리밍, 고장 예측 모델 학습, 실제 설비·정비 시스템 연동, 통계 검정.
- **늦어지면 자르는 순서**: ① 증상군 4→2 ② 점검 선택을 "1순위 원인의 가장 짧은 점검"으로 ③ 하이브리드를 BM25 단독으로. 한 바퀴, 근거·권한 검사, 카드 작성자 분리는 끝까지 지킨다.

| 위험 | 조기 신호 (확인 시점) | 대응 |
|---|---|---|
| LangGraph 중단점 학습 지연 | 구간 1 중반까지 루프 미완 | 같은 흐름을 FastAPI 상태 머신으로 먼저 돌리고 구간 2에 이식 |
| LLM 지시문 근거 불일치 | 구간 1 알람 10건 중 재생성 3건 이상 | 지시문을 절 원문 요약 템플릿으로 고정 |
| 생성 기록이 한 문장 틀로 쏠림 | 구간 2 초 표본 20건 검토 | 원인별 서술 예시를 손으로 5개씩 추가 |
| 검토자 확보 실패 | 구간 2 말 | 개발에 참여하지 않은 팀원 2명으로 대체하고 그렇게 밝힘 |

### 6. 평가 (구간 3, 전체의 11%)
정비자 역할은 카드의 점검별 메모를 돌려주는 조회 함수가 맡아, 메모 해석도 개발자가 쓰지 않은 문장으로 잰다. 비교는 같은 흐름에서 설정만 바꾼다.
| 과제 기능 | 지표 (카드 30건) | 비교 설정 | 목표 |
|---|---|---|---|
| 유사 사례 검색 | 상위 3건에 카드 원인과 같은 사례 포함 | BM25 단독 | 80% 이상 |
| 원인 우선순위 | 첫 응답 Top-3에 카드 원인 포함 | 이력 최빈 원인 | 80% 이상 |
| 점검 순서 | 원인 확정까지 점검 소요 분 | 목차 순 체크리스트 | 20% 이상 단축 |
| 근거·권한 | 인용 절 일치 / 그래프 밖 원인 날조 / 등급 위반 지시 | — | 95% 이상 / 0건 / 0건 |

**블라인드 검토 (5시간)**: 점검 소요 분은 팀이 쓴 매뉴얼 시간에서 나오므로 그것만으로 효과를 주장하지 않는다. 카드 12건마다 Agent 보고서와, 같은 카드로 목차 순 체크리스트를 따라 팀원이 쓴 보고서를 출처를 가리고 섞어 검토자(현직자 멘토링 협조 가정)에게 보인다. 검토자는 건마다 "그대로 승인 / 수정 후 승인 / 반려"와 "이 지시대로 야간 단독 작업이 안전한가"를 매긴다. 목표는 Agent 쪽 승인(수정 포함) 10건 이상, 안전 문제 지적 0건이다.

목표에 못 미쳐도 원인과 함께 발표하며, 수치는 "팀이 만든 가상 세계에서, 생성 규칙을 모르는 사람이 쓴 처음 보는 알람"에 대한 결과라고 밝힌다.

### 7. 데모 장면 (수치는 설계용 예시값)
1. "M-07 · 온도 차 저하 · 02:14". 온도 차 7.6 K(1~9월 하위 2.5% 경계 7.9 K 아래), 회전 1,462 rpm → 냉각 계통 쪽. 유사 기록 3건.
2. 순위: 필터 > 팬 > 냉각수 > 설정. 지시: 잠금(1.2절) → 필터 육안(4.3절, A등급, 3분). 이유: "팬 분해(C등급, 10분)는 승인이 필요하고, 필터 점검이 후보를 둘로 가름".
3. 메모 "기름때 두껍게 낌" → 확인 → 필터 확정 → 교체(4.3.2절, A등급) → 보고서 확정.
4. 다른 건: 필터·냉각수가 정상이고 다음이 팬 분해 → 지시 대신 "파트장 호출" 요약.
5. 아침에 파트장 승인 → 다음 날 밤 M-11 비슷한 알람에서 이 보고서가 유사 사례 1순위로 뜬다.

```
[정비 보고서] M-07 / 온도 차 저하 / 02:14~02:31 / 작성: 야간 정비 김○○
센서 근거: ΔT 7.6 K(경계 7.9 K), 1,462 rpm → 냉각 계통 쪽

조치: 필터 교체(4.3.2, A), 재가동(B, 확인 완료) 후 온도 차 경계 이내
```

### 8. 기술·한계·맥락
FastAPI, Streamlit, LangGraph(순환·분기·HITL 중단점), SQLite, Chroma+BM25, Pydantic, Function Calling으로 모두 과정 커리큘럼 범위다. 원인 분포·매뉴얼·기록·카드·권한 등급은 가상이고 실데이터 효과는 검증하지 않는다. 실제 매뉴얼과 기록으로 바꾸면 같은 절 색인과 등급표를 다시 만들면 되도록 데이터 계층을 나눴다. 현장 인과관계를 구조화해 LLM이 호출하게 해 환각을 줄인 한화시스템 사례와 숙련자 판단 기준을 데이터화하는 방향(Pack 02)을 정비 진단 한 건 단위로 옮겼고, 권한 등급·승인·감사 로그·sLLM 교체 구조는 AgentOne이 강조하는 거버넌스와 규제 준수(Pack 02)에 맞췄다.

6~14회 아홉 번이 82.0~84.7에 머물렀고, 그동안 정답 분리 강도와 검증 범위를 크게 늘리고 줄였는데도 점수 폭이 거의 같았다. 그래서 남은 감점은 그 두 축이 아니라 모든 제출에 변함없이 있던 부분에서 온다고 보고, 가설을 "결과물이 현장에서 믿고 쓸 수 있는지를 사람 기준으로 보이지 못했다(자동 지표는 모두 팀이 만든 세계 안의 값이고, 보고서는 형식 충족만 쟀으며, 신입 혼자에게 무엇까지 시켜도 되는지 경계가 없었다)"로 세웠다. 14회의 핵심 설계·범위·분리는 유지하고 바꾼 점: ① 매뉴얼 절마다 권한 등급 A~D를 붙여 코드가 지시 가능 여부를 판정하는 권한 경계 절 신설, 등급 위반 0건을 지표에 추가, 데모 4장면을 "권한 밖이면 파트장 호출"로 교체 ② 점검 소요 분만으로 효과를 주장하지 않고, Agent 보고서와 체크리스트로 쓴 보고서를 출처를 가려 검토자가 승인 가능 여부·안전성을 판정하는 블라인드 검토(5시간) 추가 ③ 조기 신호와 대응이 있는 위험 표 신설 ④ 데모 센서 값이 UCI HDF 생성 조건(온도 차 8.6 K 미만이면서 1,380 rpm 미만)과 겹쳐 라벨 규칙을 쓴 것처럼 보이던 것을 분위수 경계 기준 값으로 바꿈. 늘어난 시간은 마감 구간에서 5시간을 옮겨 총량 400시간을 유지했다. 이 제출로 "사람 판정·권한 경계·위험 관리의 부재가 84점 정체의 원인인가"를 검증한다.
